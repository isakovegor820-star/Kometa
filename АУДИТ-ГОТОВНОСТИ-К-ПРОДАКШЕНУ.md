## 1. Миграции БД: Alembic нет, схема правится руками на старте

### 1.1 [BLOCKER] Единственный механизм миграций — список колонок в коде, который правит боевую БД при каждом запуске
`app/db/session.py:18-23, 29-97, 107-124`

`init_db()` вызывает `create_all` + `_apply_light_migrations`, которая для SQLite делает `ALTER TABLE ... ADD COLUMN` по кортежу `_EXTRA_COLUMNS` (64 записи вручную). Ни Alembic, ни `alembic.ini`, ни каталога `migrations/` в репозитории нет; в `requirements.txt` пакета `alembic` нет. Комментарий на `session.py:110-111` («Для PostgreSQL используем Alembic») **не соответствует действительности** — `grep -ri alembic` даёт ровно эту строку.

Чего механизм не умеет вообще: переименовать/удалить колонку, изменить тип, добавить NOT NULL/UNIQUE/FK, бэкфилл данных, откат. Нет таблицы версий → невозможно узнать, какая схема на проде. Ошибки создания индексов глотаются молча (`session.py:120-124`).

**Воспроизведение**: `grep -ri alembic app/ requirements.txt` → одна строка комментария; `ls alembic* migrations` → пусто.
**Как исправить**: ввести Alembic (env.py + baseline-ревизия по текущей схеме), `init_db()` оставить только для dev (`create_all` под флагом), выкат — `alembic upgrade head` перед стартом процесса.

### 1.2 [CRITICAL] `_apply_light_migrations` не покрыта ни одним тестом
`grep -rln "init_db\|_apply_light\|_EXTRA_COLUMNS" tests/` → пусто. Код, который **каждый запуск** мутирует боевую базу, тестами не проверяется; список колонок ничем не сверяется с моделями. Добавление поля в `models.py` без строки в `_EXTRA_COLUMNS` даст на проде `no such column` в рантайме (упадёт всё, что читает `users`), а не ошибку на старте.

### 1.3 [HIGH] Схема свежей установки и обновлённой БД расходятся
Проверено эмпирически: база создана кодом из `HEAD`, затем к ней применён `init_db()` рабочей копии.

| | свежая (`create_all`) | обновлённая (`_EXTRA_COLUMNS`) |
|---|---|---|
| индексов | 33 | 30 (`ix_orders_partner_id`, `ix_users_partner_id`, `ix_users_personal_link_id` отсутствуют) |
| FK `users.partner_id`, `users.personal_link_id`, `orders.partner_id`, `orders.gift_activated_by` | есть | **нет** |
| `UNIQUE(gift_token)` | дубли отклоняются | **дубли принимаются** (PoC: два `INSERT` с `gift_token='DUP'` прошли) |

`_EXTRA_COLUMNS` добавляет только тип колонки: `("orders","gift_token","VARCHAR(32)")` — без UNIQUE, `("users","partner_id","INTEGER")` — без FK и индекса. Один и тот же код на двух базах ведёт себя по-разному; отчёты по партнёрам на обновлённой базе сканируют таблицу целиком. **Как исправить**: перейти на Alembic (1.1), а до этого — добавить в `_apply_light_migrations` создание недостающих индексов (`CREATE INDEX IF NOT EXISTS`) и тест, сверяющий `PRAGMA table_info`+`index_list` с `Base.metadata`.

### 1.4 [HIGH] Внешние ключи не включены
`PRAGMA foreign_keys = 0` на движке приложения (замер на живом `engine`). SQLAlchemy/aiosqlite по умолчанию не включает enforcement, а в `app/db/session.py:14` нет ни `connect_args`, ни event-листенера. Все `ForeignKey(...)` в `models.py` (включая `orders.plan_id → plans.id`, `users.referred_by → users.id`) — декларация без проверки: осиротевшие строки возможны, каскадов нет.
**Как исправить**: `event.listens_for(engine.sync_engine, "connect")` → `PRAGMA foreign_keys=ON`, затем разовая проверка целостности существующей базы.

## 3. 2FA и защита админки

### 3.1 [HIGH] Двухфакторной аутентификации нет
`grep -rni "totp\|2fa\|two.factor\|otpauth\|pyotp" app/ tests/` → **0 совпадений**. Вход — пароль (или логин+пароль), `app/web/admin/auth.py:69-124`.

### 3.2 [HIGH] Сессии не инвалидируются; выход не убивает сессию на сервере
`app/web/security.py:120-172` — cookie `expires.payload.hmac` без серверного состояния. `auth.py:146-148` при выходе лишь `delete_cookie`. Следствия: украденная cookie живёт до `ADMIN_SESSION_HOURS` (по умолчанию 12), смену/сброс пароля и увольнение сотрудника сессии не отзывают; «выйти на всех устройствах» невозможно.
**Как исправить**: хранить `session_id` в БД с полем `revoked_at`, класть его в cookie; при logout/смене пароля — инвалидировать.

### 3.3 [MEDIUM] Флаг Secure у cookie зависит от схемы запроса
`app/web/security.py:295-315`: `Secure` ставится, только если `request.url.scheme == "https"` или `ADMIN_TRUST_PROXY=true` и `X-Forwarded-Proto: https`. За TLS-терминирующим прокси без `ADMIN_TRUST_PROXY` cookie уходит **без Secure** → перехватываемая по http. Плюс `set_cookie` без `path` (`auth.py:114-123`) → cookie админки отправляется на `/sub/*` и `/payments/*`.
**Как исправить**: отдельная настройка `ADMIN_COOKIE_SECURE=true` для прода, `path="/admin"`.

### 3.4 [MEDIUM] Блокировки учётной записи нет; throttle обходится заголовком и теряется при рестарте
`security.py:319-342`, `auth.py:74-100`: 10 неудач / 10 минут **на IP**, счётчик — `dict` в памяти процесса. `client_ip()` (`security.py:241-256`) при `ADMIN_TRUST_PROXY=true` берёт первый `X-Forwarded-For` без проверки, что прокси его перезаписывает → перебор с подделкой заголовка; при перезапуске счётчики обнуляются; при нескольких воркерах лимит делится на их число. Блокировки по логину нет → распределённый перебор по одному паролю владельца не ограничен. Словарь `_attempts` растёт неограниченно (мелкая утечка памяти).
**Как исправить**: считать попытки в БД по (IP + логин), экспоненциальная задержка, лимит на логин, `X-Forwarded-For` брать справа/из доверенного прокси.

### 3.5 Что реально сделано хорошо
Пароли — PBKDF2-HMAC-SHA256 240k итераций, сравнение в постоянном времени (`security.py:43-64`); `ADMIN_LOCAL_ONLY=true` по умолчанию + allowlist (`security.py:259-270`); `docs_url=None`; все маршруты панели, кроме `login/logout`, обходят `require()` (проверено AST-разбором `app/web/admin/*.py`); журнал `admin.login_failed` пишется (`auth.py:86-96`).

### 6.1 [BLOCKER] Вебхук WATA выдаёт доступ за чужой платёж: сумма не проверяется, привязки к нашему терминалу нет

### 10.1 [HIGH] Причина всех 40 — рассинхрон объекта настроек

> **ИСПРАВЛЕНО 08.10.2026 (верификация ведущего ревью).** В первой редакции причина
> указана неточно: `tests/test_launch_copy.py:56` — это строка **докстрока**, а не вызов;
> вызывать `cache_clear()` этот файл перестал ещё раньше. Настоящий источник —
> autouse-фикстура `isolate_settings_from_env_file` в `tests/conftest.py:78,88`,
> которая вызывает `get_settings.cache_clear()` **до и после каждого теста**.
> Диагноз ниже («рассинхрон настроек») верен, ошибочна только атрибуция файла.
> Также неверно, что `test_web_tls.py` проходит в одиночном прогоне: он падает
> и сам по себе (2 падения) — это независимая поломка, а не порядковая.

`tests/conftest.py:78,88` вызывает `get_settings.cache_clear()`. После этого `get_settings()` возвращает **новый** объект, а модули, захватившие настройки при импорте (`app/main.py:48`, `app/web/security.py:27`, `app/web/payments.py:29` и др.), держат старый. Тесты, патчащие `settings`, перестают влиять на проверяемый код.

Минимальное воспроизведение (детерминированное, без зависимости от порядка):
```

python -c "import app.main as m; from app.config import get_settings;

```

Доказательство (порядок решает всё):

Все падающие файлы идут по алфавиту **после** `test_launch_copy.py`. То есть 40 «красных» — это ложные сигналы: реальный продукт в этих местах работает (проверено одиночными прогонами: `test_platega_webhook.py` — 23 passed, `test_legal_documents.py` — 17 passed). Отдельно: в паре `launch_copy + platega_webhook` прогон **зависает** (>60 с, снят по таймауту) — при рассинхронизированных настройках реестр платёжных провайдеров собирается с боевыми ключами и тест может уйти в реальную сеть.
**Как исправить**: убрать `cache_clear()` из теста (передавать настройки явно/через `monkeypatch.setenv` + сброс в `conftest` для всех), запретить сетевые вызовы на уровне conftest, добавить `pytest-randomly` или прогон в обратном порядке в CI.

## 12. Производительность и ёмкость: SQLite без WAL, один писатель

Замеры на живом `engine` приложения:
```
PRAGMA journal_mode  = delete      (WAL не включён)
PRAGMA busy_timeout  = 5000 мс
PRAGMA foreign_keys  = 0
```
`app/db/session.py:14` — `create_async_engine(url, echo=False, future=True)`, без `connect_args` и PRAGMA-листенеров; `grep -rn "journal_mode\|busy_timeout\|connect_args" app/` → пусто.

### 12.1 [HIGH] Конкурентная запись падает с `database is locked`
Воспроизведение (два писателя через `SessionMaker`):
```
писатель №1: INSERT, commit не делается
писатель №2: COMMIT -> УПАЛ через 5.2 c: OperationalError: database is locked
```
Транзакция №2 ждёт 5 секунд и падает. В вебхуке это необработанное исключение → HTTP 500 (платёж не записан), в фоновой задаче — сорванный цикл. При 200+ клиентах писателей одновременно много: 12 задач планировщика (`app/main.py:478-537`), веб-слой, вебхуки, бот.

### 12.2 [HIGH] Сессии держатся открытыми во время сетевых вызовов
`app/main.py:191-222` — одна сессия на цикл до 100 последовательных HTTP-запросов к Platega (таймаут 30 с каждый): при недоступности API это до нескольких минут удержания соединения и блокировки. То же в `autopay.reconcile` (`app/services/autopay.py:231-249`) и в `/sub/{token}` (`sub.py:522-570`).
**Как исправить**: включить WAL + `busy_timeout` (10-30 с), `synchronous=NORMAL`, убрать сетевые вызовы из транзакций (собирать данные → открывать короткую транзакцию на запись), при росте — PostgreSQL.
