## 2. Где именно поломка

Профиль `u1522748563` (UUID `6f22781e-c6e2-460b-b189-b4cc99bb78a0`) по нодам:

| Нода | `enable` | `expiryTime` (панель, UTC) | `created_at` / `updated_at` |
|---|---|---|---|
| 🇩🇪 DE (панель) | вкл | 09.10 19:52 | — |
| 🇫🇮 **FI** | **ВЫКЛ** | **08.10 19:52:50** (истёк) | 06.10 19:52:50 / 08.10 19:52:52 |
| 🇳🇱 NL | вкл | 08.10 20:40 | 06.10 20:40:44 / 06.10 20:40:44 |

Запись в БД бота: подписка №8, статус `trial`, `expires_at = 09.10.2026 18:34:50 UTC`.

**Расхождение сроков:** бот считает, что доступ живёт до 09.10, а финская панель — что до 08.10.
Панель сработала раньше, погасила профиль по своему сроку и выставила `enable=false`
(`updated_at` 08.10 19:52:52 UTC — тот же момент, что и `expiryTime`). Нидерландская панель с тем
же сроком `08.10 20:40` профиль **не** погасила, поэтому через NL тот же клиент подключается.

Заодно видно, откуда взялось расхождение: при выдаче триала 06.10 финский профиль получил
`created_at == expiryTime == 06.10 19:52:50` (то есть «срок 2 дня от создания»), а нидерландский —
`created_at == expiryTime == 06.10 20:40:44`. Бот же выдавал триал `{"days": 3}` (событие
`trial_started`, 06.10 18:34:50). Сроки на нодах разъехались ещё при выдаче: DE получил 3 дня,
FI и NL — по 2, и на FI это кончилось первым.

## 3. Почему это выглядит как «сервер лежит», и почему мониторинг молчит

Путь жалобы: человек открывает приложение → видит 🇫🇮 → подключается → **тишина**. При этом:

* Reality-рукопожатие доходит до ноды и **проходит** (см. п. 1.8), клиент даже пишет
  `tunneling request` — обрыв происходит дальше, на подстановке UUID: панель отдала Xray профиль
  с `enable=false`, и трафик не идёт;
* **подписка продолжает отдавать мёртвый конфиг FI** (проверено: `curl` подписки клиента —
  теги `Kometa-Reality-443-u1522748563`, `Kometa-Reality-8443` с адресом `77.221.147.230`).
  Сервис подписок 3x-ui собирает локацию по инбаунду и **не фильтрует выключенных клиентов**;
* **ни один экран этого не видит**: мониторинг проверяет панель, порты, ID и выдачу конфигов, но
  не проверяет, что выданный конфиг действительно проводит трафик у конкретного клиента.
  Поэтому `/status` зелёный, `location_audit` зелёный, алертов нет — а человек без связи.

Это ровно тот класс дефекта, под который в проекте уже есть инструменты
([`РАЗБОР-ЛОКАЦИЯ-НЕ-РАБОТАЕТ.md`](РАЗБОР-ЛОКАЦИЯ-НЕ-РАБОТАЕТ.md)): «локация работает, а клиент
не подключается». Добавился новый подвид — **панель погасила профиль, подписка об этом не знает**.

## 4. Что сделать сейчас

1. **Вернуть доступ по FI этому клиенту.** Важно: одной разблокировки бота **не хватит** — срок
   профиля на FI (`08.10 19:52 UTC`) уже в прошлом, и панель погасит его снова. Полное действие —
   два шага:
   1. в клиенте FI **выставить срок** как в БД бота (`09.10 18:34 UTC`);
   2. **включить** профиль — любым из способов:
      * панель FI → инбаунды `1, 2, 6` → клиент `u1522748563` → `enable`;
      * бот: команда `/unblock 1522748563` (или `/admin/users` → «Разблокировать») — обе дёргают
        [`set_enabled(..., enabled=True)`](../app/services/subscriptions.py#L476) по **всем** нодам
        (шаг «выставить срок» они не делают).

   После этого проверить: `enabled443 -> http=200 exit_ip=77.221.147.230`.
2. **Проверить остальных** — сейчас расхождение есть только у одного клиента (сверка всех 22
   профилей по трём панелям: `FI: выключено 1, DE: 0, NL: 0`). Но следующий истёкший по панели
   клиент даст ту же картину.
3. Ничего перезапускать на FI **не нужно**: панель отвечает `3/3`, Xray работает, порты открыты,
   трафик идёт.
