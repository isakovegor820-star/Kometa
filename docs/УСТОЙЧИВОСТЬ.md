# Устойчивость к блокировкам и «белым спискам»

Документ отвечает на главный вопрос честно: что наш сервис может, а что — нет.
Писался, чтобы не продавать клиентам то, чего не будет.

---

## 1. Что такое «белый список» и почему это не обходится сервером

Во время угроз БПЛА в ряде регионов мобильные операторы переводят сеть в режим ограничений:

| Режим | Что происходит | Помогает ли VPN |
|---|---|---|
| **Полное отключение** мобильного интернета | Сети нет совсем | ❌ Нет. Канала связи не существует |
| **Белый список по IP** | Разрешён трафик только к IP из списка (госуслуги, банки, VK, Яндекс, маркетплейсы) | ❌ Нет, если нашего IP в списке нет — пакеты не уходят |
| **Белый список по домену/SNI** | Разрешены соединения к определённым доменам | ⚠️ **Иногда да** — если наш вход маскируется под разрешённый домен |
| **Фильтрация по SNI/DPI (обычные блокировки)** | Режут конкретные домены/протоколы | ✅ Да, это наш основной сценарий |
| **Замедление (throttling)** | Режут скорость до отдельных сервисов | ✅ Да, частично |

**Вывод для клиентов:** мы гарантируем работу при блокировках и замедлениях. При полном
отключении сети и при жёстком белом списке по IP — не гарантируем и не обещаем. Это прописано
в ТЗ и в текстах бота: обещать «работает без интернета» — значит терять клиентов и репутацию.

## 2. Что реально повышает шансы (и что настроим на ноде)

### 2.1 Маскировка Reality под «разрешённый» домен

У VLESS+Reality в настройках есть домен маскировки (SNI). Если оператор фильтрует по домену,
выбор домена **из белого списка** даёт шанс пройти, тогда как `www.microsoft.com` в этом режиме
будет отрезан.

Практика: на ноде задаём SNI через `install_node.sh --sni <домен>`, а список кандидатов держим
в двух наборах:

* **обычный режим** (блокировки по DPI): `www.microsoft.com`, `www.apple.com`, `dl.google.com` —
  крупные зарубежные домены с TLS 1.3 и HTTP/2;
* **режим белых списков**: домен, который точно в списке у оператора в твоём регионе
  (обычно это `gosuslugi.ru`, `vk.com`, `yandex.ru`, `sberbank.ru`).

Скрипт проверяет, что выбранный домен поддерживает TLS 1.3 и HTTP/2, и что он не указывает
на наш же IP. **Проверять список нужно вручную** — он у каждого оператора и региона свой,
и меняется.

> ⚠️ Честно: это повышает шансы, но не даёт гарантии. Если фильтр по IP — SNI не спасёт.

### 2.2 Несколько точек входа

Одна нода = одна точка отказа. Минимум:

| Слой | Что даёт |
|---|---|
| 2 ноды в разных странах и разных подсетях (DE + NL) | Блокировка одной не убивает сервис |
| 2 протокола на каждой ноде (VLESS+Reality на 443/tcp и AmneziaWG на UDP) | Если режут TCP/TLS — работает UDP, и наоборот |
| Резервный порт (например, 8443) | Обход блокировок по номеру порта |
| Ссылка-подписка со всеми локациями | Клиент сам переключается в один тап, без переустановки |

### 2.3 CDN-фронт: проверено — не работает (05.10.2026)

Идея была: заходить не на наш IP, а на ближайшую точку крупного CDN, тогда первая миля короткая.
Проверка фактов её закрыла:

* **Cloudflare прямо запрещает** использование своей сети для VPN и прокси-услуг
  (Terms of Use, обновлены 05.05.2026) и оставляет за собой право удалить аккаунт без предупреждения;
* у Cloudflare из российских городов есть точки только в **Москве, Санкт-Петербурге и Красноярске** —
  ни Екатеринбурга, ни Новосибирска, ни Владивостока;
* Cloudflare **сам пишет** (документ от 23.04.2026), что российские операторы режут трафик к их сети
  до ~16 КБ на соединение, и восстановить связность они не могут. То есть даже при наличии точки
  в городе первая миля не работает;
* ни у одного CDN с точками в РФ (Gcore, Selectel, VK Cloud, Yandex Cloud, Bunny, EdgeCenter,
  DDoS-Guard, Qrator, StormWall) разрешение проксировать VPN-трафик **не подтверждено**;
  Bunny отдельно блокирует аккаунты, зарегистрированные через VPN.

**Вывод: ставку на CDN-фронт снимаем.** Вместо него работают проверенные механизмы:
несколько нод в правильных локациях + автовыбор по задержке на стороне клиента (см.
[ГЕОГРАФИЯ-И-ПИНГ.md](ГЕОГРАФИЯ-И-ПИНГ.md)).

### 2.4 Быстрая смена IP

Если IP попал в блокировку, сервис живёт ровно столько, сколько нужно на смену адреса. Поэтому
при покупке сервера смотрим:

* есть ли в панели **смена IP** и сколько она стоит (в идеале — бесплатно или символически);
* есть ли **API** для автоматизации (VDSina — есть);
* можно ли заказать **второй IP** на тот же сервер.

Инструкция «что делать, если нода перестала работать» — в `docs/ЗАПУСК.md`, раздел диагностики;
кратко: поднять вторую ноду → переключить `PANEL_INBOUND_IDS` → написать в канал, что локация
сменилась, ссылку у клиентов менять не нужно.

### 2.5 Мониторинг реальной доступности

Аптайм сервера ничего не говорит о том, работает ли VPN. Поэтому:

* `scripts/healthcheck.sh` — проверяет панель и веб-слой;
* отдельно проверяем доступность **снаружи** (внешний чекер порта), а не только изнутри;
* алерты в Telegram админу при изменении состояния (уже реализовано в боте).

## 3. Что говорить клиентам

| Ситуация | Формулировка в поддержке |
|---|---|
| Блокировки сайтов, замедление | «Работает: переключи локацию в один тап, если стало медленно» |
| Мобильный интернет режут по SNI | «Попробуй переключить локацию и протокол в приложении» |
| Белый список по IP | «В этом режиме оператор пропускает только разрешённые адреса — к сожалению, обойти это технически невозможно. Сервис заработает, как только режим снимут» |
| Полное отключение | «Сети нет — VPN работает только поверх интернета. Как только связь вернётся, доступ продолжит работать, ничего перенастраивать не нужно» |

Такая честность экономит деньги на возвратах и репутацию: клиент не считает, что его обманули.

## 4. Чек-лист при покупке сервера (с учётом устойчивости)

- [ ] 2 ноды в разных странах и **разных подсетях** (не у одного хостера, если можно)
- [ ] Смена IP доступна и недорогая; есть API
- [ ] Порты 443/tcp и UDP открыты, порт 1 Гбит/с
- [ ] Хостер не блокирует VPN по своей инициативе (проверяем правила и отзывы)
- [ ] Ноды **только за пределами РФ**: по кейсу Aeza (03.12.2025) РКН рассылает хостам списки IP
      и требует удалить VPN за 24 часа, причём детект ловит не только WireGuard/OpenVPN, но и
      Xray/Reality в «чистых» сетях
- [ ] В `.env` заполнены обе ноды, `PUBLIC_BASE_URL` — внешний адрес
- [ ] `scripts/healthcheck.sh` в cron с `--notify`
- [ ] В канале есть закреплённый пост «что делать, если не работает»
