# DNS-туннель: дежурный канал, который работает, когда не работает ничего

> **Дата:** 07.10.2026. **Роль в продукте:** четвёртый канал доступа из четырёх
> ([docs/ОБХОД-БС-ЛЮБОЙ-ГОРОД-LTE.md](ОБХОД-БС-ЛЮБОЙ-ГОРОД-LTE.md) §2). Он не заменяет VPN и не
> годится для видео: это «дежурный» доступ на время, когда обычные адреса, CDN и релеи не проходят.
> Скорость 1–6 Мбит/с, в основном Android.
>
> **Реализация:** `scripts/add_dns_tunnel.sh` (серверная часть), клиент — сторонний.

---

## 1. Почему DNS вообще проходит

Запросы к DNS — инфраструктурная необходимость: даже в режиме ограничений оператор обычно
пропускает обращения к своему резолверу. Туннель пользуется этим: данные клиента упаковываются в
DNS-запросы к **нашему поддомену**, резолвер оператора пересылает их на наш авторитативный сервер
(NS-делегирование), а тот распаковывает и проксирует трафик дальше.

Что это даёт и чего не даёт:

| | |
|---|---|
| ✅ Проходит там, где режется всё, кроме DNS | ✅ Не нужен «белый» адрес и разрешённый домен |
| ✅ Работает на любом операторе, где резолвер пересылает чужие зоны | ✅ Стоит один домен, сервер уже есть |
| ❌ 1–6 Мбит/с: переписка, почта, карты — да; видео — нет | ❌ Задержка выше обычного туннеля в разы |
| ❌ Обрывы: сессию надо переподнимать | ❌ Мобильные приложения живут не на всех платформах |

## 2. Что нужно купить и настроить

| Шаг | Что | Цена |
|---|---|---|
| 1 | Домен (любой регистратор; зона .ru дешевле, но домен не должен светиться как «VPN») | ~1 200 ₽/год |
| 2 | Делегирование: A-запись `tns.example.com` → IP сервера, NS-запись `t.example.com` → `tns.example.com` | 0 ₽ (панель регистратора) |
| 3 | Сервер: тот же зарубежный VPS (UDP/53 + внутренний порт) | 0 ₽ доп. |
| 4 | Клиент: `dnstt-client` для ПК, SSH-приложения для Android | 0 ₽ |

Распространение DNS после правки записей — до 24 часов; скрипт умеет проверять делегирование
(`--check-dns`) и не устанавливать сервер, пока зона не отвечает.

## 3. Развёртывание

```bash
# 1) Проверить делегирование домена (ничего не ставит)
./scripts/add_dns_tunnel.sh --domain t.example.com --ns-host tns.example.com \
  --server-ip 203.0.113.2 --check-dns

# 2) Посмотреть план: юнит systemd, правило iptables, пути ключей (dry-run, в сеть не ходит)
./scripts/add_dns_tunnel.sh --domain t.example.com --ns-host tns.example.com \
  --server-ip 203.0.113.2 --mode ssh --mtu 1232

# 3) Установка на сервере
sudo ./scripts/add_dns_tunnel.sh --domain t.example.com --ns-host tns.example.com \
  --server-ip 203.0.113.2 --mode ssh --mtu 1232 --apply
```

Скрипт скачивает официальный `dnstt-server` (с проверкой sha256, если передана `--sha256`),
генерирует ключи (`server.key` / `server.pub`), поднимает systemd-юнит от отдельного пользователя и
заводит UDP-трафик с 53-го порта на внутренний (по умолчанию 5300) — порт 53 обычно занят
`systemd-resolved`.

**MTU:** по умолчанию 1232; в ограниченных мобильных сетях ставьте 512–1200. Ошибка
`requester payload size ... is too small` означает, что MTU надо снизить.

## 4. Клиенты и честное ограничение по платформам

| Платформа | Чем подключаться | Готовность |
|---|---|---|
| ПК (Windows/macOS/Linux) | `dnstt-client` (бинарники на dnstt.network) | ✅ |
| Android | SSH-режим: HTTP Injector, HTTP Custom, DarkTunnel | ✅ |
| iOS | HTTP Injector | ⚠️ по отзывам сообщества канал живёт хуже |
| Android «в один тап» | [WhiteDNS](https://github.com/WhiteDNS/WhiteDNS-Android) | ❌ **не совместим**: WhiteDNS работает на движках StormDNS/CottenDns, а не на dnstt |

Если хочется «одно приложение и красиво» на Android — это отдельный проект: разворачивать
StormDNS/CottenDns под WhiteDNS. Решение принимаем по факту спроса: для дежурного канала важнее
работа, а не удобство установки.

Клиентская команда для ПК выглядит так:

```bash
dnstt-client -udp <IP-сервера>:53 -pubkey-file server.pub t.example.com 127.0.0.1:7000
# дальше приложение подключается к локальному SOCKS/HTTP на 127.0.0.1:7000
```

## 5. Как проверить, что канал живой

```bash
systemctl status dnstt-server          # служба запущена и перезапускается сама
journalctl -u dnstt-server -n 50       # ошибки ключей, порта, MTU
ss -ulnp | grep 5300                   # сервер слушает внутренний порт
dig @<IP-сервера> t.example.com        # делегирование доехало до нашего NS
```

С телефона: включить приложение, поставить MTU 512, проверить, что открывается лёгкая страница.
Если не поднимается — снизить MTU и повторить; если и это не помогает, домен мог попасть под
блокировку, и зону надо менять.

## 6. Эксплуатация и границы

* **Скорость.** 1–6 Мбит/с; один канал тянет несколько клиентов на переписку, но не «весь сервис».
* **Срок жизни.** Как у любого канала: недели–месяцы. Домен, попавший под блокировку, меняется за
  вечер — клиентам выдаётся новая зона и новый публичный ключ.
* **Кто получает доступ.** Канал выдаём **по запросу в поддержке** (клиент пишет, мы даём конфиг):
  публично не рекламируем — иначе он выгорает первым.
* **Риск для узла.** Нагрузка на DNS-сервер заметна хостеру; держим отдельный аккаунт и помним, что
  этот же адрес используется как выход.
* **Не тариф.** В подписке канала нет (он не VLESS): это сервисная опция на время ограничений,
  как и остальной аварийный уровень ([docs/АВАРИЙНЫЙ-УРОВЕНЬ-ПЛАН.md](АВАРИЙНЫЙ-УРОВЕНЬ-ПЛАН.md)).
