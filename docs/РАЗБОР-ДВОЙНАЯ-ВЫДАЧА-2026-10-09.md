# Разбор: одна оплата — два месяца доступа (заказ #8, 09.10.2026)

Инцидент: клиент оплатил 60 ₽ за тариф «1 месяц», а подписка продлилась дважды —
сначала «до 14.11.2026 (36 дн.)», через несколько секунд «до 14.12.2026 (66 дн.)».
Админам пришли два одинаковых уведомления «Оплата получена · Заказ #8 · 60 ₽».

Разбор сделан по боевому серверу (`150.241.106.75`, `/home/vpnadmin/kometa`):
БД `data/kometa.db`, лог `logs/bot.log`, дампы Platega-транзакций в логе httpx.

---

## Коротко

**Вопрос 1: почему 60 ₽, а не 120 ₽.** Это не ошибка. Тариф «1 месяц» = 120 ₽.
Покупатель пришёл по реферальной ссылке **@qmler**, поэтому сработала скидка
приглашённому 50 % на первую оплату: `120 − 60 = 60 ₽`. Код `KOMETA-R6BKQHKT`
в сообщении — это персональный реферальный код @qmler, применённый автоматически
(в `.env` прода `REFERRAL_DISCOUNT_PERCENT=50`, потолок `REFERRAL_DISCOUNT_MAX_RUB=0`).

**Вопрос 2: почему два месяца.** Один и тот же заказ №8 подтвердили **три
независимых пути**: фоновый опрос Platega (раз в 30 с), вебхук и кнопка клиента
«Проверить оплату». Кнопка прочитала заказ, пока он ещё был `pending`, затем
~10 секунд ждала ответ платёжной системы; за это время опрос успел выдать месяц.
`mark_paid` проверял статус **по объекту в памяти** (`if order.status == "paid"`),
где статус остался `pending`, — и выдал доступ второй раз. Дополнительно
реферальная программа приняла второе подтверждение за «продление» и начислила
@qmler ещё +14 дней.

Итог: покупатель получил 66 дней вместо 36 (лишние 30), @qmler — 44 дня вместо 30
(лишние 14). Деньги за лишний месяц не получены.

## Вопрос 1: откуда скидка 60 ₽

Цепочка (БД прода, время UTC):

1. `09.10 03:21:46` — покупатель (id 26) заходит по реферальной ссылке
   → `referral_joined` (event 91), `users.referred_by = 12`,
   лениво создаётся персональный промокод @qmler:
   `promo_codes` id 7, `code = KOMETA-R6BKQHKT`, `kind = referral`,
   `owner_user_id = 12`, `percent = 50`, `max_discount_rub = 0`, `uses_limit = 50`.
2. `09.10 03:22:05` — триал 3 дня (`trial_started`, event 92): подписка id 21,
   срок до 12.10.2026 03:22.
3. `09.10 03:22:51` — создан заказ №8. При расчёте цены `promo_service.resolve()`
   перебирает кандидатов: код, введённый руками (пусто) → **код пригласившего
   (referred_by = 12)** → персональная ссылка (нет) → партнёр (нет). Первый
   подходящий — `KOMETA-R6BKQHKT`.
   `calc_discount_rub(120, 50, 0) = 120 * 50 // 100 = 60` → к оплате 60 ₽.
4. `order_created` (event 93): `amount 60, base_amount 120, discount 60,
   promo KOMETA-R6BKQHKT`; `promo_applied` (event 94); после оплаты
   `promo_redeemed` (event 96, `promo_redemptions` id 5).

Строка заказа в БД:

```
id=8 user_id=26 plan_id=1 kind=renew amount_rub=60 base_amount_rub=120
discount_rub=60 promo_code=KOMETA-R6BKQHKT provider=platega_sbp status=paid
external_id=16b7a6e3-be43-4a51-b25a-9286f4b647ef
created_at=2026-10-09 03:22:51.616862  paid_at=2026-10-09 03:24:34.429535
```

В чате клиент видел ровно это: «Скидка 60 ₽ по промокоду KOMETA-R6BKQHKT уже учтена.
Заказ #8 на 60 ₽» (кадр записи, 07:22 по времени телефона).

**Вывод:** 60 ₽ — это 50 % скидка приглашённому по реферальной ссылке, а не сбой
и не «промокод, который кто-то подобрал». Такая скидка заложена в продукт:
«друг по ссылке получает скидку 50 % на первую оплату» (`app/services/promo.py`,
`app/services/referral.py`). Отдельно стоит решить продуктово: 120 ₽ − 50 % = 60 ₽
за месяц — ниже себестоимости (в `docs/ФИНМОДЕЛЬ.md` экономика считалась под
другую скидку: в коде дефолт `REFERRAL_DISCOUNT_PERCENT=30`, на проде стоит 50).

## Причина в коде

### 1. Идемпотентность держалась на объекте в памяти

`app/services/orders.py`, `mark_paid()` **до правки**:

```python
if order.status == "paid":
    return await subscriptions.get_subscription(session, order.user_id), True
```

`order` приходит от вызывающего. Кнопка «Проверить оплату»
(`app/bot/handlers/buy.py`, `cb_check_payment`) читает заказ один раз в начале,
затем делает сетевой запрос в платёжную систему и только потом зовёт
`finalize_order → mark_paid`. Всё это время в объекте `status="pending"`, хотя в
БД заказ уже `paid` (его закоммитил опрос). Проверка по памяти пропускает вторую
выдачу: `subscriptions.activate_plan()` продлевает срок ещё раз
(`panel.update_user(extend_days=days)` считает дни от текущего срока в панели).

### 2. Подтвердить один заказ могут четыре пути, и они не разведены

* `job_check_platega` — опрос Platega каждые 30 с (`app/main.py`);
* `POST /platega/webhook` — вебхук (`app/web/payments.py`);
* кнопка «Проверить оплату» — `order:check:<id>` (`app/bot/handlers/buy.py`);
* ручное подтверждение админа и автосверка переводов (`app/services/autopay.py`,
  `app/web/admin/orders.py`) — у них та же точка входа `mark_paid`.

Общего «замка» нет: `SELECT ... FOR UPDATE` в SQLite невозможен, а `status`
менялся обычным присваиванием.

### 3. Окно гонки широкое

* проверка транзакции у Platega ~10 с (медленный API — отдельный повод разобраться);
* опрос держит транзакцию открытой, пока не отработают панели DE/FI/NL
  (~1.6 с в этом инциденте);
* в момент инцидента совпали все три: опрос, вебхук и кнопка клиента.

### 4. Реферальный бонус не проверял, за какой заказ он уже начислен

`app/services/referral.py`, `reward_on_payment()`: признак «продление» — это
`ref.paid_order_id is not None`, то есть «хоть одна оплата уже была». Повторное
подтверждение **того же** заказа прошло как продление и дало @qmler +14 дней
(`referral_bonus_days_renewal`).

## Что исправлено (в этой рабочей копии, на прод НЕ выкатывалось)

Прод и локальная копия до правки совпадали побайтно (md5), поэтому патч
применим к проду как есть.

1. **`app/services/orders.py` — атомарный захват заказа.**
   Вместо проверки по памяти — одна инструкция:

   ```python
   claimed = await session.execute(
       update(Order).where(Order.id == order.id, Order.status == "pending").values(**values)
   )
   await session.refresh(order)
   if not claimed.rowcount:
       if order.status in {"paid", "refunded"}:
           return await subscriptions.get_subscription(session, order.user_id), True
       return None, False
   ```

   Право выдать доступ получает ровно один вызов: второй (вебхук, опрос, кнопка,
   админ) видит `rowcount = 0` и выходит, не трогая срок.

2. **`app/bot/handlers/buy.py` — атомарное переоткрытие закрытого заказа.**
   `finalize_order()` больше не пишет `order.status = "pending"` присваиванием
   (это затирало бы результат параллельного пути), а делает
   `UPDATE ... WHERE status IN ('canceled','expired')` и перечитывает объект;
   если заказ уже обработан — выходит.

3. **`app/services/referral.py` — одна награда на одну оплату.**
   `if ref.paid_order_id == order.id: return None` — повторное подтверждение того
   же заказа не считается продлением.

4. **Регрессионные тесты `tests/test_payment_race_repro.py`** — воспроизводят
   ровно этот сценарий: заказ прочитан «давно» в одной сессии, выдан в другой,
   затем устаревший объект отдаётся в `mark_paid`. До правки оба теста падали
   (`assert False is True`, `renewals_count == 1`), после — проходят.

Проверка: `pytest -q` по всему дереву — зелёный (см. прогон в конце разбора).

## Что стоит доработать отдельно

* **Скорость Platega.** `GET /transaction/{id}` отвечает ~10 с — это и есть ширина
  окна гонки. Если у провайдера есть более быстрый вебхук/батч-метод, опрос
  стоит перевести на него; заодно проверить таймауты и keep-alive httpx-клиента.
* **Панель и БД не транзакционны.** Если панель не ответила, заказ всё равно
  остаётся `paid` (админ получает алерт), а повторный `mark_paid` уже не
  сработает. Разумно хранить `grant_pending` и повторять выдачу, а не помечать
  заказ оплаченным до успеха панели.
* **Дубль `ORDER_PAID` в `autopay.py`.** Событие пишется даже когда
  `mark_paid` вернул `already=True` — статистика может задваивать оплату.
* **Продуктово:** 50 % на первую оплату при цене 120 ₽ = 60 ₽ за месяц. Проверить
  по `docs/ФИНМОДЕЛЬ.md`, что скидка не уводит первую оплату в минус.
