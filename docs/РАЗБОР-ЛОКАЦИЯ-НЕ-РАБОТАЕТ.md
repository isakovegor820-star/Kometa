# Разбор: «локация не работает» — как назвать причину, а не гадать

**Симптом владельца:** «🇳🇱 Нидерланды не работают» — и при этом экраны говорят разное:
`/status` зелёный, в `/admin/nodes` красное, на экране локаций в боте страны нет, в Telegram —
алерт. Так происходит потому, что **каждый экран показывает свой слой** клиентского пути:
панель, порт, сервис подписок или настройку ID. Инструмента, который проходит по всем слоям
сразу и называет причину, не было — теперь есть.

* Инструмент: [`app/tools/location_audit.py`](../app/tools/location_audit.py)
* Тесты: [`tests/test_location_audit.py`](../tests/test_location_audit.py)
* Соседние инструменты: [`check_nodes`](../app/tools/check_nodes.py) (только сверка ID),
  [`ping_node`](../app/tools/ping_node.py) (только один порт),
  [`emergency_check`](../app/tools/emergency_check.py) (готовность аварийного уровня).

---

## 1. Запуск

На сервере, из каталога бота (`~/kometa` или `/home/vpnadmin/kometa`):

```bash
# основной прогон: три попытки на каждый сетевой слой, пауза 5 с — видно «через раз»
.venv/bin/python -m app.tools.location_audit --repeat 3 --interval 5

# тот же отчёт в JSON — можно переслать в чат целиком:
# UUID клиентов маскируются, пароли из адресов вырезаются
.venv/bin/python -m app.tools.location_audit --repeat 3 --interval 5 --json

# что будет проверяться — без единого запроса в сеть
.venv/bin/python -m app.tools.location_audit --dry-run
```

**Код возврата:** `0` — все локации «работает»; `1` — есть проблема **или** локацию не удалось
подтвердить («нечего проверять»). Годится для дежурной проверки в скрипте/cron.

Локально (dev-копия с `PANEL_TYPE=fake`) инструмент запускается, но честно скажет
«⚪ нечего проверять»: у заглушки нет ни адреса клиента, ни настоящего сервиса подписок.
Это ожидаемый результат, а не поломка.

## 2. Как читать вывод

Для каждой локации печатаются **все слои** — и рядом с каждым то, чем он подтверждён:

```text
🇩🇪 Германия (primary) · 150.241.106.75 (sub_base) · панель http://150.241.106.75:2053 [xui]
  панель:     ✅ отвечает 3/3 · 0.0 с
  инбаунды:   1 «Kometa-Reality-443» vless:443 tcp · 2 «Kometa-AWG-51820» wireguard:51820 udp · 4 «Kometa-Reality-8443» vless:8443 tcp
  ID:         настроено 1, 2, 4 · в панели 1, 2, 4 · ✅ сходятся
  порт 443 «Kometa-Reality-443» vless: ✅ открыт 3/3 · 14 мс
  порт 8443 «Kometa-Reality-8443» vless: ✅ открыт 3/3 · 21 мс
  подписка:   http://150.241.106.75:2096/sub/ · HTTP 404 · 2 конфига · host в конфигах: 150.241.106.75:443, 150.241.106.75:8443
  вердикт:    ✅ работает
              → подтверждено: панель 3/3 · порты 443 (14 мс), 8443 (21 мс) · 2 конфига · ID сходятся

🇫🇮 Финляндия (fi) · 77.221.147.230 (nodes.host) · панель http://77.221.147.230:2053 [xui]
  ...
  порт 8443 «Kometa-Reality-8443» vless: ❌ не пускает 0/3 · таймаут TCP (5.0 с)
  вердикт:    ✅ работает
              → подтверждено: панель 3/3 · порты 443 (14 мс) · 2 конфига · ID сходятся
              ⚠️ часть портов не пускает: 8443 — клиент может подключиться на остальных, но запасной канал мёртв

🇳🇱 Нидерланды (nl) · 146.255.188.12 (nodes.host) · панель http://146.255.188.12:2053 [xui]
  панель:     ✅ отвечает 3/3 · 0.0 с
  ID:         настроено 1, 2, 3 · в панели 1, 4 · ❌ нет настроенных ID: 2, 3
  порт 443 «Kometa-Reality-443» vless: ❌ не пускает 0/3 · таймаут TCP (5.0 с)
  порт 8443 «Kometa-Reality-8443» vless: ❌ не пускает 0/3 · таймаут TCP (5.0 с)
  вердикт:    🔴 порт не пускает
```

Что здесь важно:

| Строка | Что означает | На что смотреть |
|---|---|---|
| `панель: … N/M` | сколько попыток из `--repeat` панель ответила и сколько секунд это заняло | `0/M` — панель не отвечает; `1/M` — «через раз» (в разделе 4 объяснено, почему это не приговор) |
| `инбаунды:` | фактический состав панели (**сырой** список, без фильтра по ID) | пусто при живом ответе — панель пуста, это тоже диагноз |
| `ID: настроено / в панели` | сверка `inbound_ids` из БД с панелью — **тот же расчёт, что у `check_nodes`** | `❌ нет настроенных ID` — новые клиенты на локацию не создаются |
| `порт <N>` | TCP-проба **каждого** TCP-инбаунда (не «первого успешного») | закрыт один из двух — запасной канал мёртв, локация при этом жива |
| `подписка:` | задан ли адрес, отвечает ли сервис, сколько конфигов отдал, какой HOST внутри | `HTTP 404` — это **норма**: сервис ответил на несуществующего клиента, значит жив; `❌ не ответил` — не жив |
| `вердикт:` | одна из шести причин (раздел 3) | это и есть ответ на вопрос «почему» |
| `⚠️` | «работает, но не полностью»: часть портов, нестабильность, лишние инбаунды, чужой HOST в конфигах | чинить не срочно, но знать надо |

`--repeat 3` нужен потому, что панель и порт умеют отвечать **через раз**, и однократная
проверка врёт в обе стороны. Печатается доля успехов (`3/3`, `1/3`), а локация не хоронится
из-за одной неудачной попытки. Повторяются сетевые слои — панель и порты; сверка ID берётся из
одного прогона `check_nodes`, чтобы диагноз не разошёлся с админкой.

## 3. Вердикты: что значит каждый

| Вердикт | Когда ставится | Что это значит для клиента |
|---|---|---|
| ✅ `работает` | панель ответила, все TCP-порты пускают, конфиги отдаются, ID сходятся | подключится; запасной канал тоже работает |
| 🔴 `порт не пускает` | панель ответила, TCP-инбаунды есть, но **ни один** порт не принял соединение | **не подключится**: фаервол/провайдер/сменившийся адрес |
| 🔴 `конфиг не выдаётся` | порт пускает, но адреса подписок нет, сервис молчит или конфигов нет ни у одного клиента | локация **молча** выпадет из подписки: в приложении её просто не будет |
| 🟠 `настройка разошлась` | панель и порт в порядке, но настроенные `inbound_ids` в панели отсутствуют | действующие подписки работают, **новые клиенты** на локацию не создаются |
| 🟠 `панель не отвечает` | API панели не ответил ни на одну попытку | может работать: порт проверяется отдельно, и если он открыт — клиенты подключаются |
| ⚪ `нечего проверять` | ни адреса клиента, ни сервиса подписок, ни сверки ID (пустая нода или заглушка панели) | судить не о чем — инструмент не выдумывает «работает» |

Порядок вердиктов — по клиентскому пути: сначала «дойдёт ли клиент до порта», потом «получит ли
конфиг», и только затем настройки. Разошедшиеся ID при закрытом порте — не то, что чинят первым.

## 4. «Панель не отвечает» и «порт не пускает» — разные диагнозы

Это два **независимых** слоя, и раньше они выглядели одинаково — отсюда половина путаницы.

| | Панель | Порт клиента |
|---|---|---|
| Что проверяется | API управления: `GET /panel/api/inbounds/list` — отвечает ли и проходит ли авторизация | TCP-соединение с портом инбаунда «глазами клиента» |
| Кто ходит | бот (сервис) | клиент в приложении (и проба — тоже с сервиса) |
| Код | [`XuiPanel.check_health`](../app/panels/xui.py#L619) | [`app/services/probe.py`](../app/services/probe.py): TCP + замер, шаги `tcp`/`tls` |
| Типичная причина отказа | 3x-ui упал, сменился токен, порт панели закрыт по IP-allowlist | фаервол ноды, смена IP, сгоревшая подсеть, фильтр у оператора |
| Если упало | новые клиенты и статистика недоступны, **уже выданные конфиги работают** | **клиент не подключится**, сколько бы панель ни была здорова |

Почему это важно на практике: **панель 3x-ui обычно слушает только `127.0.0.1` и закрыта
IP-allowlist** — снаружи её порт 2053 не отвечает, и это нормально. Поэтому «панель не
отвечает» с чужой точки зрения ничего не говорит о клиенте, и наоборот: панель может быть
недоступна из интернета, а локация — прекрасно работать.

### Почему `/status` про клиента ничего не говорит

`/status` собирается в [`_service_status`](../app/web/sub.py#L163). Это срез **двух слоёв**, и
ни один из них не отвечает на вопрос «работает ли локация целиком»:

* `panel` — «API панели ответил на список инбаундов». Это **сырой** список: он не смотрит
  `inbound_ids` и потому остаётся зелёным, даже когда настроенные ID разошлись и новые клиенты
  не создаются ([`check_health`](../app/panels/xui.py#L619) делает тот же запрос, что
  `_fetch_inbounds`, а фильтрует уже [`list_inbounds`](../app/panels/xui.py#L635));
* `probe` — состояние **последнего** замера порта: проба идёт раз в 5 минут, поэтому после
  правки конфигурации страница ещё какое-то время показывает прошлое состояние;
* `subscriptions_available` — «есть хотя бы одна живая панель», а не «подписка этой локации
  отдаёт конфиги».

Чего `/status` не видит **вообще**:

1. расхождение `inbound_ids` («настройка разошлась»);
2. пустой или нерабочий `sub_base` («конфиг не выдаётся»);
3. отсутствие профиля клиента в инбаундах локации;
4. дубль `panel_url`, когда «страна» на самом деле чужая панель.

Ровно эти четыре причины и дают «NL не работает» при зелёном `/status`. Поэтому статусная
страница не заменяет аудит: она отвечает «сервис в целом жив», а не «эта локация доведёт
клиента до коннекта».

Ещё об одной ловушке: `sub.py` при сбое выдачи **не показывает ошибку**, а пишет её в лог
([`logger.warning("Панель %s не отдала конфиги…")`](../app/web/sub.py#L540)) и продолжает
собирать подписку из остальных локаций. Так локация исчезает из подписки бесшумно — ни на
одном экране этого не видно.

### Симптом → причина → действие

| Что видно | Слой | Причина | Действие |
|---|---|---|---|
| `/admin/nodes`: «отвечает» **и** «порт не пускает» | порт | TCP не проходит с сервиса | проверить фаервол/адрес ноды: `ping_node --host <нода> --port <порт>` |
| Telegram `node:<код>:probe` «порт не пускает клиента» | порт | то же, замер подтверждён | то же; после починки перевыдавать конфиги не нужно |
| Telegram `node:<код>` «не отвечает» | панель | API/токен/порт панели | `systemctl status x-ui` на ноде; клиентов не трогать, если порт открыт |
| `/admin/nodes`: «нет инбаундов [3]» | ID | `inbound_ids` разошлись с панелью | вписать фактические ID из отчёта → «Проверить ноды» → `sync_inbounds --apply` |
| Telegram `node:<код>:inbounds` | ID | то же | то же |
| Экран локаций в боте: страна пропала | ID/панель | `list_inbounds` упал, ошибка ушла в лог | отчёт назовёт ID и панель |
| `/admin/nodes`: «нет адреса подписки» | подписка | пустой `sub_base`/`host` | вписать «Адрес сервиса подписок» |
| У одного клиента в подписке нет страны, у других есть | подписка | нет профиля этого клиента в инбаундах локации | `sync_inbounds --apply` |
| В приложении у всех «🇳🇱» не подключается, пинг есть | подписка | чужой HOST в конфигах (`shareAddr` инбаунда) | сверь `host в конфигах` с адресом ноды (инструмент предупредит) |
| Страна в приложении не в общем списке | канал | локация помечена `reserve`/`cdn` — отдельная группа автовыбора | это не поломка: смотреть `channel` в `/admin/nodes` |
| «Не работает» висит после починки | — | проба/проверка идут раз в 5 минут | нажать «Проверить ноды» или подождать цикл |

## 5. Диагноз по Нидерландам

Дано (проверено снаружи и из кода, без доступа к прод-`.env`):

* все три ноды отвечают по TCP на 443: `150.241.106.75`, `77.221.147.230`, `146.255.188.12`;
* порт панели 2053 у DE отвечает снаружи, у FI/NL — таймаут: это **нормально**, 3x-ui обычно
  слушает `127.0.0.1` и закрыт IP-allowlist;
* публичный `/status?format=json` показывает все три локации как `ok:true`;
* жалоба владельца — не про `/status`, а про `/admin/nodes`, дашборд, экран локаций в боте и
  алерты в Telegram.

### 5.1. Что `ok:true` уже исключает и что им не проверяется

`ok:true` в `/status` означает: панели **отвечают** из сервиса (сырой список инбаундов), а
состояние порта берётся из последней пробы. Значит:

* «панель не отвечает» — **маловероятно** (но проверить надо: `/status` кэширует ответ на
  минуту, а между обновлениями проба могла измениться);
* «порт не пускает» — **исключено только на момент замера**: если в `/status` у NL
  `probe: "ok"`, порт на момент замера пускал; смотреть надо `probe_at` (давность);
* «настройка разошлась», «конфиг не выдаётся», дубль панели — **не проверяются `/status`
  вообще** (см. раздел 4). А ведь именно эти три причины дают «NL не работает» при зелёной
  статусной странице.

Отсюда порядок разбора: сначала аудит (все слои), потом — конкретный экран.

### 5.2. Гипотезы: что подтверждено кодом, а что требует прогона на сервере

«Подтверждено кодом» = механизм существует и даёт ровно такой симптом; «нужен прогон» = без
боевой базы и панели конкретные значения назвать нельзя.

| # | Гипотеза | Как выглядит на экранах | Подтверждение | Статус |
|---|---|---|---|---|
| H1 | `inbound_ids` ноды NL снова разошлись с панелью (ID автоинкремент: после пересоздания панели те же инбаунды получили другие номера) | `/admin/nodes`: красное «нет инбаундов» рядом с зелёным «отвечает»; экран локаций в боте теряет NL; Telegram `node:nl:inbounds`; новые клиенты NL не получают | `list_inbounds` фильтрует по ID и падает ([`_target_inbounds`](../app/panels/xui.py#L467), текст «не найдены инбаунды … проверь inbound_ids» — [xui.py:482](../app/panels/xui.py#L482)); `health` при этом зелёный, а `last_check_ok` становится `False` ([alerts.py:293](../app/services/alerts.py#L293)); экран локаций ловит `PanelError` и молча пропускает страну ([`cb_locations`](../app/bot/handlers/subscription.py#L165)) | ✅ механизм; ⏳ нужны фактические ID (`location_audit`, `check_nodes`) |
| H2 | Порт(ы) NL не проходят **с сервиса** (фаервол, смена IP у хостера, отдельный порт 8443) | Telegram `node:nl:probe` «порт не пускает клиента»; `/admin/nodes` «порт 443 не пускает»; у клиентов нет пинга | шаг пробы `tcp`/`tls` = «порт измерен» ([`MEASURED_STAGES`](../app/services/probe.py), [`probe_verdict`](../app/services/probe.py)); замер по каждому порту хранится в `Node.last_probe_ports` ([models.py:569](../app/db/models.py#L569)) | ✅ механизм; ⏳ прогон: внешняя проверка 443 ≠ проверка с сервиса, и 8443 надо смотреть отдельно |
| H3 | Сервис подписок NL не отдаёт конфиги: пустой `sub_base`, закрытый 2096, битый `subId` | в приложении у клиента нет «🇳🇱 Нидерланды», при этом админка может быть зелёной | ошибка выдачи глотается с `logger.warning` ([sub.py:540](../app/web/sub.py#L540)) → локация исчезает **бесшумно**; адрес собирается из `host`, если `sub_base` пуст ([`Node.subscription_base`](../app/db/models.py#L515)) | ✅ механизм; ⏳ прогон: блок `subscription` в `--json` (`configs`, `hosts`, `clients_checked`) |
| H4 | Дубль `panel_url`: нода NL смотрит на панель DE | «нидерландские» профили ведут на немецкий сервер; карточка NL в админке показывает DE-инбаунды; одна панель опрашивается дважды | `registry.for_node` строит клиента по `node.panel_url`; `check_nodes` предупреждает «адрес указан дважды»; подписка добавит те же конфиги второй раз под другим именем | ✅ механизм; ⏳ `select code,panel_url from nodes` |
| H5 | Нода NL выключена (`is_active=0`) | страны нет ни в подписке, ни на экране локаций; в админке нода показана выключенной | реестр берёт только активные ноды ([registry.py:84](../app/panels/registry.py#L84)) | ✅ механизм; ⏳ прогон sqlite |
| H6 | У части клиентов нет профиля в инбаундах NL (выданы до появления локации или после смены ID) | у одного клиента NL в подписке нет, у другого есть | [`get_configs`](../app/panels/xui.py#L941) ищет клиента по uuid в инбаундах и падает, если его там нет; досоздаёт [`sync_inbounds`](../app/tools/sync_inbounds.py) | ✅ механизм; ⏳ прогон: `subscription.clients_checked` в отчёте |
| H7 | Локация помечена каналом `reserve`/`cdn` | в приложении NL не в общем списке, а в группе «резерв» | метка канала в имени профиля ([`channel_mark`](../app/web/subscription_format.py)) | ✅ механизм; ⏳ `select code,channel from nodes` |
| H8 | Экраны показывают устаревшее состояние (проба раз в 5 минут) | «не работает» висит после починки | проба и проверка нод идут по расписанию; свежесть видна в отчёте | ✅ механизм; ⏳ свежесть в выводе |

Короткий вывод по коду: **«NL не работает» при зелёном `/status` вероятнее всего означает одну
из трёх причин — разошедшиеся ID (H1), не выдающиеся конфиги (H3, H6) или дубль панели (H4)**.
Порт (H2) и панель (H3-панель) проверяются `/status` и, скорее всего, уже исключены — но это
надо подтвердить прогоном, потому что статус кэшируется и показывает последний замер, а не
«сейчас».

### 5.4. Что нужно от владельца (данные, а не догадки)

1. Полный вывод инструмента с сервера — он же и есть диагноз:

   ```bash
   cd ~/kometa            # или /home/vpnadmin/kometa
   .venv/bin/python -m app.tools.location_audit --repeat 3 --interval 5 --json \
     > /tmp/location-audit.json && cat /tmp/location-audit.json
   ```

   JSON можно переслать в чат целиком: UUID клиентов замаскированы, пароли вырезаны.

2. Что записано в боте (сверка `panel_url` — это H4/H5, `sub_base`/`channel` — H3/H7):

   ```bash
   sqlite3 data/kometa.db "select code,title,host,panel_url,inbound_ids,sub_base,is_active,channel,
     last_check_ok,last_check_error,last_probe_stage,last_probe_error,last_probe_at from nodes;"
   ```

3. Живые алерты по NL (какой именно слой ругается и как давно):

   ```bash
   sqlite3 data/kometa.db "select id,kind,fingerprint,status,severity,repeat_count,last_seen_at,message
                           from alerts where fingerprint like 'node:nl%' order by id desc limit 10;"
   ```

4. **Где именно** видно «NL не работает»: какой экран, какой текст, и у всех ли клиентов сразу.
   Если у одного клиента NL нет, а у других есть — это H6 (профиль клиента), и тогда нужен его
   `uuid`/токен подписки: инструмент проверяет первых трёх клиентов, а конкретного можно
   посмотреть через `/sync` и админку.

## 6. Границы инструмента (чтобы не ждать лишнего)

* **Это диагностика, а не починка.** Инструмент ничего не пишет в БД и в панель; правки — в
  `/admin/nodes`, `.env` и через [`sync_inbounds --apply`](../app/tools/sync_inbounds.py).
* **Проверка идёт с сервиса, а не из телефона клиента.** Закрытый порт с сервиса — почти
  всегда закрыт и для клиента, но обратное неверно: маршрут оператора может резать адрес,
  который сервис видит открытым. Клиентский путь проверяется замерами (`docs/ЗАМЕРЫ-ЭТАП-0.md`) и
  самим клиентом по `SUBSCRIPTION_TEST_URL`.
* **TLS-рукопожатие не проверяется** (только TCP): SNI инбаунда абстракция панели не отдаёт —
  для этого есть [`ping_node --sni`](../app/tools/ping_node.py).
* **UDP-профили (AmneziaWG, Hysteria2, TUIC) TCP-пробой не проверяются** — открытый порт про
  них ничего не говорит; инструмент пишет «TCP-инбаундов нет» и не выдаёт это за аварию.
* **Порт проверяется по списку из панели.** Если панель не отдала инбаунды, порт не
  проверяется вовсе — состояние порта честно помечается как «не проверялся», а не
  «не пускает».
* **`--repeat` повторяет сетевые слои** (панель, порты). Сверка ID берётся из одного прогона
  `check_nodes`, поэтому при нестабильной панели её результат может быть «список не получен» —
  это видно в отчёте, а не спрятано.
* **Клиентов для проверки выдачи — до трёх** (первый может быть без профиля на локации).
  Если ни один не подошёл, в отчёте будет `clients_checked` и текст ошибки панели.
* **Фоновые пробы могут быть выключены** (`NODE_PROBE_ENABLED=false`): аудит всё равно проверит
  порты вручную и предупредит об этом, но в админке, `/status` и боте данных пробы не будет —
  «нет данных пробы» там означает «пробы не идут», а не «мы не успели».
