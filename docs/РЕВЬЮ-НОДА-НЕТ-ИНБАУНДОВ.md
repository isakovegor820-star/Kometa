# Ревью: «Нода «🇳🇱 Нидерланды»: нет инбаундов [3]»

**Сигнал из центра алертов:**

```
Нода «🇳🇱 Нидерланды»: нет инбаундов
в панели не найдены инбаунды [3] (проверь inbound_ids)
Внимание · node_degraded · первый раз 1 ч назад · повторов: 16 · node:nl:inbounds
В работе у владелец — проблема ещё не закрыта
```

**Что проверено:** весь путь сигнала — планировщик → `alerts.check_nodes` → `XuiPanel` →
карточка алерта, плюс следствия для выдачи доступа и ссылки-подписки. Код не менялся:
только чтение плюс прогон сценария на временной БД (приложение А). Тесты трёх затронутых
модулей зелёные: `tests/test_alerts.py tests/test_panel_xui.py tests/test_multinode.py` — 52 passed,
полный набор — 863 теста, exit 0.

> **Уточнение от 08.10.2026 (после правок).** Сообщение, которое пришло в Telegram
> («порт не пускает клиента. панель не отдала инбаунды: …»), родилось **не** в разобранном ниже
> пути `check_nodes`, а в пробе «глазами клиента»: `probe_panel` не получила список инбаундов и
> объявила «порт не пускает клиента», хотя до порта не дошла
> ([app/services/probe.py:150](../app/services/probe.py#L150), [app/main.py:214](../app/main.py#L214)).
> Путь `check_nodes` даёт второй алерт — warn `node_degraded` «нет инбаундов». Оба сигнала про одну
> причину и оба починены: статус по пунктам раздела 7 — в
> [ПЛАН-ПОЧИНКА-НОДА-НЕТ-ИНБАУНДОВ.md](ПЛАН-ПОЧИНКА-НОДА-НЕТ-ИНБАУНДОВ.md). Находки F11–F19
> остаются в силе как список задач.

## 1. Короткий вердикт

1. **Алерт по факту не врёт.** Текст — дословный ответ панели
   ([app/panels/xui.py:471](../app/panels/xui.py#L471)): панель ноды ответила, авторизация
   прошла, инбаунды в ней **есть**, но ни у одного нет `id=3`. То есть в БД у ноды `nl`
   в `inbound_ids` лежит несуществующий ID. Это не «нода упала» и не «в панели нет инбаундов» —
   при всей серьёзности проблемы заголовок описывает её неверно.
2. **«16 повторов за час» — не аномалия и не 16 аварий.** `repeat_count` равен числу проверок:
   планировщик ходит раз в 5 минут ([app/main.py:248](../app/main.py#L248)) → 12/час, а «1 ч назад»
   в интерфейсе — округление вниз, от 60 до 119 минут ([app/web/ui.py:248-249](../app/web/ui.py#L248)).
   16 проверок ≈ 1 ч 20 мин. Никаких «двух ботов» или сбоя таймера для объяснения не нужно.
3. **Но код вокруг сигнала устроен так, что этот алерт:**
   * получает заголовок «нет инбаундов» не только при нехватке ID: туда же попадают пустая панель,
     ответ-не-список и осечка второго запроса к панели (F1), а падение самой панели уходит
     в `node_down` с обезличенным текстом (F2);
   * **нельзя закрыть** удалением или выключением ноды — только успешной проверкой (F3);
   * теряет статус «взято в работу» на следующей же проверке, а если карточка висит «В работе»
     долго — значит проверка для неё уже не идёт либо строка осиротела (F4, F19);
   * живёт на одной странице с зелёным бейджем «отвечает» у той же ноды (F5);
   * не показывает реальные ID инбаундов панели, хотя именно они и нужны для починки (F6, F7).
4. **Следствие для клиентов:** существующие подписки страну не теряют (конфиги собираются из
   «сырых» инбаундов, [app/panels/xui.py:872](../app/panels/xui.py#L872)), а **новые клиенты
   на этой ноде не создаются** ([app/panels/xui.py:656](../app/panels/xui.py#L656)) — и это
   молча глушится, потому что для нод ошибка панели не срывает выдачу
   ([app/services/subscriptions.py:198-206](../app/services/subscriptions.py#L198)). В логе
   остаётся «Нода xui не приняла клиента» — **без страны** (F8, F9).

Итого: инцидент — операционный (ID разошлись), но за 5 минут его не видно, а закрыть его
штатными кнопками нельзя. Ниже — трасса, находки, что делать сейчас и что править.

## 3. Первопричина: что означает это сообщение

`_target_inbounds()` работает так ([app/panels/xui.py:460-472](../app/panels/xui.py#L460)):

```python
inbounds = await self._fetch_inbounds()          # GET /panel/api/inbounds/list
if not inbounds:
    raise PanelError("в панели 3x-ui нет ни одного инбаунда")
if not self.inbound_ids:
    return inbounds                              # пусто = все инбаунды
wanted  = set(self.inbound_ids)
selected = [item for item in inbounds if int(item.get("id") or 0) in wanted]
missing  = sorted(wanted - {int(item.get("id") or 0) for item in selected})
if missing:
    raise PanelError(f"в панели не найдены инбаунды {missing} (проверь inbound_ids)")
```

Значит, для ноды `nl` верно ровно это: **панель ответила и список инбаундов непустой, но ID `3`
в нём нет** — при этом `inbound_ids` ноды содержит `3`. Ранжированные механические причины:

1. **ID устарел после переустановки/сброса панели.** `id` в SQLite панели — автоинкремент: после
   пересоздания базы те же по смыслу инбаунды получают ID 1 и 2, а в боте остаётся 3.
2. **ID скопирован из другой страны.** У каждой ноды свои ID, они задаются в админке
   ([docs/МУЛЬТИГЕО-ЗАПУСК.md:197](МУЛЬТИГЕО-ЗАПУСК.md#L197)), но подсказка в форме — просто «1,2»,
   а сверки с панелью при сохранении нет (F10).
3. **`panel_url`/`panel_token` ноды указывают на другую панель** (старый сервер, соседняя страна):
   в ней своих ID 3 нет.
4. **Инбаунд удалён в панели**, а запись в боте осталась (пересоздание Reality/AWG вручную,
   чистка инбаундов после экспериментов).
5. **`3` — это «третий инбаунд» той же панели, а не выдуманный ID.** Скрипт установки сам
   советует завести второй Reality на резервном порту
   ([scripts/install_node.sh:659-661](../scripts/install_node.sh#L659)), а переименование
   AWG-инбаунда создаёт новый и оставляет старый — в скрипте для этого даже есть legacy-имя
   `Kometa-AWG-51820` ([scripts/install_node.sh:49-52](../scripts/install_node.sh#L49),
   [:744-761](../scripts/install_node.sh#L744)); ещё один инбаунд добавляет
   [scripts/add_ws_inbound.sh](../scripts/add_ws_inbound.sh). На панели, где Reality = 1, AWG
   пересоздавали, а WS добавляли позже, `3` — вполне живой ID, просто **не тот**, что записан у ноды.

Отпечаток `node:nl:inbounds` заодно говорит, **где** искать: это нода из таблицы `nodes`
(у основной панели из `.env` отпечаток был бы `node:primary:inbounds`,
[app/services/alerts.py:197-198](../app/services/alerts.py#L197)). Отдельно стоит проверить, что
`panel_url` ноды не совпадает с `PANEL_URL` основной панели: `registry.all_panels` не сравнивает
адреса ([app/panels/registry.py:66-71](../app/panels/registry.py#L66)), и одна и та же панель
может опрашиваться дважды — как «основная» и как «нода», с разными списками ID.

Версия «ложный алерт из-за сетевой осечки» почти исключена: сетевые сбои дают другие тексты
(«панель не ответила за 15 с», «HTTP 401», «не-JSON»), а один и тот же текст повторился 16 раз
подряд. То есть сигнал стабильный и содержательный — но оформлен так, что читается как «в панели
нет инбаундов».

## 4. Находки

Важное (P0): **F1** заголовок врёт · **F2** причина падения теряется · **F3** алерт не закрывается
при удалении/выключении ноды · **F4** «взято в работу» слетает.
Среднее (P1-P2): **F5** «отвечает» рядом с алертом · **F6** админка врёт про сеть · **F7** реальные
ID не видны · **F8** в логах нет страны · **F9** ошибка ноды глушится · **F10** нет валидации ID ·
**F15** ops-скрипты проверяют грепом · **F18** нет дедупа панелей · **F19** отпечаток не уникален.
Мелочи: **F11** двойной запрос · **F12** отпечаток по изменяемому коду · **F13** счётчик и имя
алерта · **F14** противоречивая пара · **F16** кэш инбаундов · **F17** связка карточки по индексу.

### F1. Заголовок «нет инбаундов» ставится и при других причинах — **важно**

`check_nodes` ловит **любое** исключение из `list_inbounds()` и кладёт его текст в `entry["error"]`
([app/services/alerts.py:200-210](../app/services/alerts.py#L200)), после чего ветка
`elif entry["error"]` **всегда** поднимает `node_degraded` с жёстко заданным заголовком
«Нода «…»: нет инбаундов» ([app/services/alerts.py:227-233](../app/services/alerts.py#L227)).

Важная оговорка (проверено отдельным прогоном): «классические» сбои панели — таймаут, 401, HTTP 500,
не-JSON — до этой ветки **не доходят**: `health()` дёргает тот же эндпоинт и падает первым
([app/panels/xui.py:576-584](../app/panels/xui.py#L576)), поэтому они дают `node_down` (и там теряют
причину — F2). Заголовок «нет инбаундов» достаётся ошибкам, случившимся **после успешного
`health()`**:

* отсутствующие ID — [xui.py:471](../app/panels/xui.py#L471) (наш случай);
* пустая панель — «в панели 3x-ui нет ни одного инбаунда» ([xui.py:463-464](../app/panels/xui.py#L463));
* ответ-не-список — «неожиданный формат ответа» ([xui.py:456-457](../app/panels/xui.py#L456));
* осечка второго запроса к панели: тот же эндпоинт вызывается дважды (F11), и сбой именно второго
  вызова даёт «нет инбаундов» при живом `health()`.

То есть заголовок врёт в трёх случаях из четырёх перечисленных. Заготовка для правильного
разделения уже есть и не используется: вид `panel_error` («Ошибка панели», warn) объявлен в
[app/services/alerts.py:34](../app/services/alerts.py#L34) и нигде не поднимается.

### F2. Реальная причина падения ноды теряется — **важно**

`XuiPanel.health()` ([app/panels/xui.py:576-584](../app/panels/xui.py#L576)) обязан вернуть `bool`
и потому глотает текст ошибки. Дальше в ветке `not entry["ok"]` `entry["error"]` всегда пустая
строка, и алерт получает generic-подпись «панель не ответила на проверку»
([app/services/alerts.py:223](../app/services/alerts.py#L223)). Проверено: панель отвечает 500 на
`/panel/api/inbounds/list` → `entry = {"ok": False, "error": ""}` → `message='панель не ответила на проверку'`.
Отличить таймаут от 401 от «нет маршрута» по алерту невозможно, хотя исключение с текстом было
внутри `health()` секундой раньше.

Отдельно: `tests/test_alerts.py:144` проверяет, что в сообщении есть `ConnectTimeout`, — но тест
использует `StubPanel`, который **бросает** из `health()`. Настоящая `XuiPanel.health()` не бросает
никогда, поэтому тест подтверждает поведение, которого в бою не бывает (ложная уверенность).

### F3. Алерт нельзя закрыть штатной кнопкой: удаление и выключение ноды его не трогают — **важно**

* `node_delete` закрывает только `node:{code}`
  ([app/web/admin/infra.py:300](../app/web/admin/infra.py#L300)) — отпечаток `node:{code}:inbounds`
  остаётся открытым навсегда, причём с `node_id` уже удалённой строки.
  Проверено: после удаления ноды в списке остаётся `('node:nl:inbounds', 'open')`.
* `node_toggle` ([app/web/admin/infra.py:260-282](../app/web/admin/infra.py#L260)) алерты не трогает
  вовсе.
* Проверки идут только по активным нодам ([app/main.py:141](../app/main.py#L141),
  [app/web/admin/infra.py:326](../app/web/admin/infra.py#L326)), поэтому автозакрытие
  ([app/services/alerts.py:238-240](../app/services/alerts.py#L238)) для выключенной ноды уже не сработает.

Итого: выключил сломанную ноду, чтобы не мешала, — алерт остался висеть в «Открытых» навсегда,
и его придётся закрывать руками. Именно это и означает «проблема ещё не закрыта».

Отдельная мина на будущее: `Alert.node_id` — внешний ключ **без** `ON DELETE`
([app/db/models.py:391](../app/db/models.py#L391)), и при закрытии алерта он не обнуляется, а
`db.delete(node)` выполняется раньше ([app/web/admin/infra.py:296](../app/web/admin/infra.py#L296)).
В SQLite внешние ключи выключены, поэтому сейчас удаление проходит; в PostgreSQL (о котором прямо
говорит [app/db/session.py:58-61](../app/db/session.py#L58)) удаление ноды с любым её алертом упадёт
с `IntegrityError`.

### F4. «Взято в работу» сбрасывается следующей проверкой — **важно**

```python
alert.status = STATUS_OPEN if alert.status == STATUS_ACK else alert.status   # alerts.py:85
```

`raise_alert` вызывается на **каждой** проверке, пока держится проблема, и потому каждые 5 минут
возвращает ack-нутый алерт в `open`. Проверено: `ack` → следующая проверка → `open`; при этом
`resolved_by` («владелец») остаётся. То есть карточка, которую видит пользователь, через ≤5 минут
потеряет строку «В работе у …», а вкладка «В работе» опустеет — хотя никто ничего не закрывал.

Для одноразовых алертов (платёж без заказа) такое «переоткрытие» осмысленно, для повторяющегося
сигнала о состоянии ноды — нет: владелец теряет отметку о том, что проблему уже взяли.

Обратная сторона медали: если карточка **долго** висит в «В работе», значит `raise_alert` для этого
отпечатка уже не вызывается — либо нода выключена/удалена (F3), либо в таблице есть строка-дубль,
которую цикл проверки не видит (F19). По одной карточке эти два случая не различить, а «повторов: N»
в обоих заморожен.

### F5. Нода одновременно «отвечает» и «нет инбаундов» — **средне**

`node.last_check_ok = bool(entry["ok"])` ([app/services/alerts.py:214](../app/services/alerts.py#L214))
истинно, даже когда инбаунды не найдены. Следствия на экранах:

* `/admin/nodes` — зелёный бейдж «отвечает» ([app/web/templates/nodes.html:89-95](../app/web/templates/nodes.html#L89));
* дашборд — то же ([app/web/templates/dashboard.html:241-244](../app/web/templates/dashboard.html#L241));
* счётчик «живых» нод `nodes_alive` ([app/web/admin/infra.py:157](../app/web/admin/infra.py#L157))
  считает такую ноду живой.

Так как это поле — единственное машинное состояние ноды в БД, любая будущая автоматика
(например, предохранитель продаж) будет считать сломанную ноду здоровой.

### F6. Страница нод при неверном ID врёт про сеть — **средне**

`_panel_views` ловит **любое** исключение из `list_inbounds()` и показывает
«панель не ответила — нажми «Проверить ноды»» либо «показаны данные прошлой проверки»
([app/web/admin/infra.py:120-138](../app/web/admin/infra.py#L120)), а карточка панели — «Инбаунды
не видны. Проверь адрес и токен панели» ([app/web/templates/nodes.html:270-275](../app/web/templates/nodes.html#L270)).
При этом панель **ответила** и вернула внятную причину — она уходит только в `logger.info`.

Усугубляет: на этой странице таймаут 1.2 с ([app/web/admin/infra.py:53-54](../app/web/admin/infra.py#L53)),
а в проверке нод — 15 с ([app/panels/xui.py:238](../app/panels/xui.py#L238)). Медленная, но живая
панель на странице выглядит мёртвой, а в алертах — нормальной; два экрана противоречат друг другу.

### F7. Реальные ID инбаундов нигде не видны — **средне**

Карточка «Панели в подписке» строит список через `panel.list_inbounds()`, а тот фильтрует по
`inbound_ids` и падает, если нужного ID нет. Поэтому при ровно этой аварии оператор не видит
на экране **ни одного** реального ID и вынужден идти в саму панель 3x-ui. То, что нужно для
починки (фактический список `id` + какие из настроенных отсутствуют), интерфейс не показывает.

### F8. В логах нет страны: все ноды называются `xui` — **средне**

`XuiPanel.name = "xui"` ([app/panels/xui.py:228](../app/panels/xui.py#L228)), а логи и счётчики
неудач пишут именно `panel.name`:

* [app/services/subscriptions.py:205](../app/services/subscriptions.py#L205) — `failed.append(panel.name)`
  → «Триал выдан без нод: xui» ([app/services/subscriptions.py:268](../app/services/subscriptions.py#L268));
* [app/services/subscriptions.py:242](../app/services/subscriptions.py#L242) — «Нода xui не обновила клиента»;
* [app/web/sub.py:314](../app/web/sub.py#L314), [:329](../app/web/sub.py#L329) — «Панель xui не отдала конфиги».

По журналу нельзя понять, какая страна сломалась, — а имя локации в панели уже есть
(`location_title`, проставляется реестром, [app/panels/registry.py:107-109](../app/panels/registry.py#L107)).

### F9. Ошибка ноды глушится, клиент молча теряет локацию — **средне**

`_create_on_panels` для нод (`index > 0`) ловит `PanelError`, пишет строку в лог и продолжает
([app/services/subscriptions.py:198-206](../app/services/subscriptions.py#L198)); `sub.py` так же
пропускает панель, не отдавшую конфиги ([app/web/sub.py:311-315](../app/web/sub.py#L311)).
Решение «нода не срывает выдачу» верное, но у него нет обратной связи: клиент получает подписку
без страны, никто ему об этом не говорит, а алерт «нет инбаундов» — единственный след, и он
warn-уровня в админке (в Telegram об этом не сообщается: `job_node_health` смотрит только на
`entry["ok"]`, [app/main.py:154-168](../app/main.py#L154)).

### F10. `inbound_ids` не валидируется, а парсеров строки — три — **средне**

* Форма сохраняет что угодно: `_clean_ids` только расставляет запятые
  ([app/web/admin/infra.py:77-80](../app/web/admin/infra.py#L77)).
* Реестр молча выбрасывает нечисловые токены:
  `[int(x) for x in node.inbound_ids.replace(" ", "").split(",") if x.strip().isdigit()]`
  ([app/panels/registry.py:61](../app/panels/registry.py#L61)).
* Для основной панели — третий, отдельный парсер ([app/config.py:241](../app/config.py#L241)).
* `_clean_ids` молча режет строку до 64 символов ([infra.py:80](../app/web/admin/infra.py#L80),
  колонка `String(64)` — [app/db/models.py:297](../app/db/models.py#L297)): длинный список ID теряет
  хвост без предупреждения.

Последствие: опечатка `3x` или `3 ,` не даёт ошибки, а **расширяет** выдачу на все инбаунды
панели (пустой список = «все»), при этом оператор уверен, что ограничил ноду одним инбаундом.
Обратная ошибка (ID, которого нет) даёт как раз наш алерт.

### F11. Каждая проверка ноды — два одинаковых запроса — **мелко**

`health()` и `list_inbounds()` дергают один и тот же `GET /panel/api/inbounds/list`
([app/panels/xui.py:579](../app/panels/xui.py#L579) и [xui.py:453](../app/panels/xui.py#L453)).
Проверено: журнал запросов к панели — `['/panel/api/inbounds/list', '/panel/api/inbounds/list']`.
Второй запрос может упасть отдельно от первого и породить ложную деградацию.

### F12. `fingerprint` привязан к изменяемому коду ноды — **мелко**

Отпечаток — `node:{code}`. Код правится в форме (upsert по коду,
[app/web/admin/infra.py:202-222](../app/web/admin/infra.py#L202)), а алерты за ним не мигрируют:
после смены кода старые отпечатки никто не закрывает (проверки идут уже под новым), и они висят
в «Открытых» вечно.

Хуже: смена кода создаёт **вторую** ноду — upsert ищет строку по коду
([app/web/admin/infra.py:218-222](../app/web/admin/infra.py#L218)), старая активная строка остаётся
и продолжает опрашиваться своим старым клиентом, а `registry.invalidate` вызывается только для
нового кода ([app/web/admin/infra.py:240](../app/web/admin/infra.py#L240)). То есть «переименовал
ноду» = «завёл дубль», который никто не видит в списке как дубль.

### F13. `repeat_count` не отличает «висит то же самое» от «сломалось снова» — **мелко**

Счётчик растёт на каждой проверке ([app/services/alerts.py:83](../app/services/alerts.py#L83)),
поэтому «повторов: 16» читается как 16 аварий, хотя это 16 опросов за 80 минут. Отдельного
признака «состояние не менялось» нет, `first_seen` тоже не отделён от `created_at`.

Ещё две мелочи того же узла: при повторе **не обновляется `title`**
([app/services/alerts.py:82-88](../app/services/alerts.py#L82)) — переименованная нода остаётся
в алерте под старым именем (обновляются только `message`, `last_seen_at` и `status`); а «16»
одинаково правдоподобно читается как «12 подъёмов планировщика + 4 ручных нажатия „Проверить ноды“»
([app/web/admin/infra.py:312-346](../app/web/admin/infra.py#L312)), так что по счётчику нельзя
отличить автоматические проверки от ручных.

### F14. Противоречивая пара алертов — **мелко**

Если деградировавшая нода падает целиком, ветка `not entry["ok"]` поднимает `node_down`, но
`node:{code}:inbounds` не закрывает ([app/services/alerts.py:217-226](../app/services/alerts.py#L217)).
В центре оказываются одновременно «нет инбаундов» и «не отвечает».

### F15. Серверные скрипты знают только основную панель и проверяют ID грепом — **средне**

`scripts/preflight.sh:185-208` и `scripts/healthcheck.sh:150-167` сверяют ID только из `.env`
(`PANEL_INBOUND_IDS`) и ничего не знают про таблицу `nodes` (grep по `sqlite3` в обоих скриптах
пуст). На мультигео-конфигурации предполётная проверка зелёная, пока нода сломана.

Хуже: наличие ID они проверяют грепом по сырому JSON — `grep -q "\"id\":${id}[,}]"`. В ответе
`/panel/api/inbounds/list` есть вложенный массив `clientStats`, и у каждого его элемента **своё**
поле `id` ([MHSanaei/3x-ui: internal/xray/client_traffic.go](https://raw.githubusercontent.com/MHSanaei/3x-ui/main/internal/xray/client_traffic.go),
`ClientTraffic.Id int json:"id"`; наш собственный клиент читает этот массив —
[app/panels/xui.py:617-621](../app/panels/xui.py#L617)). Поэтому grep может совпасть со строкой
трафика и отрапортовать «все инбаунды на месте» там, где инбаунда с таким ID уже нет.
`preflight.sh` вдобавок печатает список ID через `grep -o '"id":[0-9]*'` — там id инбаундов
перемешаны с id статистики. Проверять надо `.obj[] | .id` через `jq`: сам бот разбирает только
верхнеуровневые элементы ([app/panels/xui.py:451-458](../app/panels/xui.py#L451)).

### F16. Кэш инбаундов в админке не сбрасывается при правке ноды и отдаёт сколь угодно старый список — **мелко**

`_inbounds_cache` ([app/web/admin/infra.py:53-57](../app/web/admin/infra.py#L53)) очищается только
кнопкой «Проверить ноды» ([infra.py:349](../app/web/admin/infra.py#L349)); сохранение, включение и
удаление ноды сбрасывают лишь кэш клиентов реестра ([infra.py:240](../app/web/admin/infra.py#L240),
[:273](../app/web/admin/infra.py#L273), [:297](../app/web/admin/infra.py#L297)). Свежесть держится
на TTL 60 с, а при ошибке показывается прошлый список **без ограничения по возрасту**
([infra.py:127-134](../app/web/admin/infra.py#L127)) — с подписью «панель не ответила», даже если
ошибка была «нет инбаундов [3]». То есть страница «Ноды» — не доказательство ни наличия, ни
отсутствия инбаунда.

### F17. Карточка панели связывается с нодой по индексу при разных сортировках — **мелко**

`_panel_views` берёт ноду как `nodes[index - 1]`
([app/web/admin/infra.py:100-107](../app/web/admin/infra.py#L100)), при том что реестр сортирует
ноды только по `priority` ([app/panels/registry.py:68](../app/panels/registry.py#L68)), а страница
и планировщик — по `priority, id` ([infra.py:151](../app/web/admin/infra.py#L151),
[main.py:141](../app/main.py#L141)). При равных приоритетах (по умолчанию 100) порядок не определён,
и инбаунды одной страны могут оказаться в карточке другой — ровно на том экране, по которому
оператор сверяет ID.

### F18. Панели не дедуплицируются по адресу: одна панель может опрашиваться дважды — **средне**

`registry.all_panels` безусловно добавляет основную панель и все активные ноды
([app/panels/registry.py:66-71](../app/panels/registry.py#L66)); если нода указывает на ту же
`panel_url`, что и `PANEL_*`, панель опрашивается дважды — с разными `inbound_ids`. Тогда
«основная» проверка зелёная, а нода ругается на `[3]`, хотя инбаунды в панели есть. В подписке это
даёт дубль локации (имена разводятся суффиксом « (2)»,
[app/web/subscription_format.py:236-238](../app/web/subscription_format.py#L236)), а трафик
считается дважды ([app/web/sub.py:327](../app/web/sub.py#L327)). Для нашего инцидента это версия,
которую надо исключить в первую очередь (шаг 4 рунбука).

### F19. Отпечаток не уникален: строка-дубль «зависает» вместе со своим статусом — **средне**

У `Alert.fingerprint` нет уникального индекса — только обычный
([app/db/models.py:390](../app/db/models.py#L390)), а `raise_alert` и `resolve_by_fingerprint`
всегда работают ровно с одной строкой — `max(id)`
([app/services/alerts.py:76-81](../app/services/alerts.py#L76),
[:113-118](../app/services/alerts.py#L113)). Если открытых строк с одним отпечатком оказалось две,
«нижняя» больше не обновляется и не закрывается никогда: её счётчик заморожен, её `ack` не
сбрасывается — карточка может висеть «В работе» не потому, что проблема жива, а потому что строка
осиротела. Гонка `SELECT`→`INSERT` ничем не защищена (в SQLite её воспроизвести не удалось, но и
гарантий от неё нет: `flush` без уникального ключа, [app/services/alerts.py:90-102](../app/services/alerts.py#L90)).

Именно поэтому стоит посмотреть на сырые строки, а не на карточку:

```sql
SELECT id, status, repeat_count, node_id, created_at, last_seen_at
FROM alerts WHERE fingerprint = 'node:nl:inbounds' ORDER BY id;
```

Больше одной строки — лишние надо закрыть руками, а сам отпечаток сделать уникальным (либо
закрывать/обновлять все строки отпечатка, а не только последнюю).

## Приложение А. Как это проверено

Сценарий на временной SQLite-базе (боевая не затронута): `XuiPanel` на `httpx.MockTransport`
(панель с инбаундами 1 и 2) + нода `nl` с `inbound_ids="3"`, затем `alerts.check_nodes`,
как в планировщике. Ключевые строки вывода:

```
health() = True
list_inbounds() → в панели не найдены инбаунды [3] (проверь inbound_ids)
запросов к панели: ['/panel/api/inbounds/list', '/panel/api/inbounds/list']   # F11

check_nodes → [{'code': 'nl', 'ok': True,
                'error': 'в панели не найдены инбаунды [3] (проверь inbound_ids)', 'inbounds': 0}]
node.last_check_ok = True                                  # F5
алерт: kind=node_degraded fingerprint='node:nl:inbounds'   # как в проде
       title='Нода «🇳🇱 Нидерланды»: нет инбаундов'

health=True + сбой list_inbounds (HTTP 500 на втором запросе,
пустая панель, ответ-не-список) → title='…: нет инбаундов'                            # F1
16 проверок              → repeats=16                                                 # F13
ack → следующая проверка → open                                                       # F4
delete node              → node:nl:inbounds остаётся open (node_id=1, строки нет)     # F3
XuiPanel + HTTP 500      → health()=False → node_down:
                           message='панель не ответила на проверку'                   # F2
```

Здесь важна аккуратность: заголовок «нет инбаундов» при HTTP 500 получен на **заглушке**
с `health() == True` (так проверялась ветка кода). У настоящей `XuiPanel` тот же HTTP 500 роняет
сначала `health()` — и получается `node_down` с обезличенным текстом (последняя строка выше).
Именно так это и проверил независимый прогон, и это уточнение внесено в F1.

Дополнительно проведены два независимых прохода по коду: (1) верификация 12 утверждений прогонами
pytest (14 собственных тестов в `/tmp`, репозиторий не менялся) — два утверждения были уточнены
(границы F1 и поведение `raise_alert` в F4/F13), остальные подтверждены; (2) аудит кэшей реестра,
админ-страницы и ops-скриптов — из него F16-F19, а также уточнения F3 (PostgreSQL), F10 (обрезка

## 9. Ответ одной строкой

Сигнал настоящий и указывает на расхождение ID инбаундов у ноды `nl`, но кодовый путь вокруг него
надо починить в трёх местах: **разделить «нет инбаундов» и «ошибка панели»**, **закрывать оба
отпечатка при удалении/выключении ноды** и **перестать сбрасывать `ack` на каждом опросе**.
Остальное (зелёный бейдж, «панель не ответила» вместо реальной причины, `xui` в логах) —
это то, из-за чего пятиминутная починка превращается в расследование.
