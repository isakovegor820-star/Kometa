# План починки: «Нода 🇳🇱 Нидерланды: порт не пускает клиента»

**Сигнал (как он пришёл):**

```
⚠️ Нода 🇳🇱 Нидерланды: порт не пускает клиента.
панель не отдала инбаунды: в панели не найдены инбаунды [3] (проверь inbound_ids)
```

Дополняет ревью [`docs/РЕВЬЮ-НОДА-НЕТ-ИНБАУНДОВ.md`](РЕВЬЮ-НОДА-НЕТ-ИНБАУНДОВ.md): там разобран путь
проверки нод (`node_degraded`), здесь — **путь пробы**, из которого пришло именно это сообщение,
и план правок. Статус правок отмечается в разделе 6.

## 1. Что происходит сейчас (трасса сигнала)

Сообщение в Telegram — это **склейка двух строк** из разных мест:

| # | Место | Что делает |
|---|-------|-----------|

| 2 | [app/main.py:196](../app/main.py#L196) | пары «активная нода + клиент её панели» |
| 3 | [app/services/alerts.py:269](../app/services/alerts.py#L269) | `check_probes` → `probe_panel(panel, node.host)` |
| 4 | [app/services/probe.py:150-152](../app/services/probe.py#L150) | `panel.list_inbounds()` упал → `ProbeResult(ok=False, stage="panel", detail="панель не отдала инбаунды: …")` |

Параллельно, раз в 5 минут, идёт вторая проверка — и она про ту же причину:

| # | Место | Что делает |
|---|-------|-----------|
| 1 | [app/main.py:297](../app/main.py#L297) | `job_node_health` каждые 5 минут |

**Итог:** на одну причину — два алерта и одно сообщение в Telegram, и **главное из них врёт**:
«порт не пускает клиента» читается как проблема фаервола/сети, хотя проба до порта не дошла.
Правда лежит во втором предложении — «панель не отдала инбаунды».

## 2. Корневая причина

**Расхождение конфигурации:** у ноды `nl` в таблице `nodes` записан `inbound_ids`, содержащий `3`,
а панель этой ноды отдаёт список инбаундов, в котором `id=3` нет.

Что это значит на практике — варианты по убыванию вероятности (проверяются на сервере, раздел 7):

1. **ID устарел после переустановки/сброса панели.** `id` — автоинкремент: после пересоздания базы
   те же инбаунды получают ID 1 и 2, а в боте осталось 3.
2. **ID скопирован из другой страны.** У каждой панели своя нумерация; подсказка в форме — «1,2».
3. **`panel_url`/`panel_token` ноды ведут на чужую панель** (старый сервер, соседняя страна).
4. **Инбаунд удалён/пересоздан** (переименование Reality/AWG создаёт новый ID, старый остаётся).
5. **Нода указывает на ту же панель, что основная** (`PANEL_URL`): одна панель опрашивается дважды
   с разными `inbound_ids` (см. F18 в ревью). Проверяется одним запросом к БД.

Доказательств «порт закрыт» в сигнале **нет вообще**: проба вернула `stage="panel"` — она не
дозвонилась не до порта, а до списка инбаундов. Это дефект кода (раздел 4, P0-1), а не факт о ноде.

## 4. Дефекты кода, которые надо закрыть

P0 — сигнал врёт и его нельзя закрыть:

- **P0-1. Проба объявляет «порт не пускает», не проверив порт.** `stage` различает `tcp`/`tls`
  (порт проверен) и `panel`/`config` (не проверен), но `check_probes` этого не использует:
  [probe.py:140-152](../app/services/probe.py#L140), [alerts.py:283-294](../app/services/alerts.py#L283).
- **P0-2. Две проверки дают два алерта на одну причину**, а заголовок `node_degraded` жёстко
  «нет инбаундов» даже когда причина другая (пустая панель, ответ-не-список, HTTP 500 после
  успешного `health()`): [alerts.py:227-237](../app/services/alerts.py#L227).
- **P0-3. У `node_down` нет причины.** `health()` возвращает `bool` и глотает текст ошибки,
  в алерт уходит «панель не ответила на проверку»: [xui.py:576-584](../app/panels/xui.py#L576),
  [alerts.py:223](../app/services/alerts.py#L223).
- **P0-4. Алерты ноды нельзя закрыть.** Удаление закрывает только `node:{code}`; выключение — ничего;
  `:inbounds` и `:probe` остаются открытыми навсегда: [infra.py:296-310](../app/web/admin/infra.py#L296).
- **P0-5. `ack` сбрасывается на каждом опросе** — карточка «в работе» теряет владельца через 5 минут:
  [alerts.py:86](../app/services/alerts.py#L86).
- **P0-6. `last_check_ok=True` при провалившейся выдаче** — зелёный бейдж «отвечает» рядом с алертом:
  [alerts.py:215](../app/services/alerts.py#L215).
- **P0-7. Фактические ID панели нигде не видны**: `list_inbounds()` падает, а админка показывает
  «панель не ответила» вместо текста ошибки: [infra.py:120-134](../app/web/admin/infra.py#L120).

P1 — чтобы это не повторилось:

- **P1-1. `inbound_ids` не валидируется**: `_clean_ids` режет строку до 64 символов и пропускает
  мусор; реестр молча выбрасывает нечисловое, и пустой список = «все инбаунды» (расширение выдачи
  вместо ошибки): [infra.py:77-80](../app/web/admin/infra.py#L77), [registry.py:61](../app/panels/registry.py#L61).
- **P1-2. В логах нет страны** — все ноды зовутся `xui`: [subscriptions.py:204](../app/services/subscriptions.py#L204).
- **P1-3. Кэш инбаундов не сбрасывается при правке/включении/удалении ноды** — страница показывает
  сколь угодно старый список: [infra.py:53-57](../app/web/admin/infra.py#L53).
- **P1-4. Нет инструмента «покажи, что реально в панели»** — оператор идёт в 3x-ui руками.

Отложено осознанно (описано в ревью, F11-F19): дедуп панелей по адресу, уникальный индекс
отпечатка, семантика `repeat_count`, jq в ops-скриптах, self-heal второй ноды при смене кода.
Причины — в разделе 8.

## 5. План исправления

1. **Разделить «проба не дошла» и «порт не пускает»** (P0-1). В `ProbeResult` — признак
   «порт реально проверялся» (`stage` ∈ `tcp`/`tls`), в ноде — шаг пробы `last_probe_stage`.
   Проба без замера: не поднимает `node_probe_failed`, закрывает старый такой алерт, пишет
   причину в ноду.
2. **Одна причина — один честный алерт** (P0-2): `panel_error` для ошибок панели после успешного
   `health()`, `node_degraded` — только для «панель жива, выдать нечего».
3. **Причина падения ноды в алерте** (P0-3): `check_health()` → `(ok, error)`.
4. **Реальные ID панели в тексте ошибки** (P0-7): `в панели не найдены инбаунды [3]; панель отдаёт:
   1 «Kometa-Reality-443», 2 «Kometa-AWG-990»`.
5. **Алерты закрываются** (P0-4): `resolve_node_alerts()` для `node:{code}`, `:inbounds`, `:panel`,
   `:probe` — при удалении, выключении (и кнопкой, и галочкой в форме) и для неактивных нод.
6. **`ack` не слетает** (P0-5): повтор не переоткрывает взятый в работу алерт.
7. **Честное состояние ноды** (P0-6): `last_check_ok = ok and not error` (и такой же признак `ready`
   уходит в счётчики админки, flash «Проверить ноды» и Telegram), плюс колонки `last_check_error`,
   `last_probe_error`, `last_probe_stage`.
8. **Админка перестаёт врать** (P0-7, P1-3): сырой список инбаундов, текст `PanelError` в карточке,
   сброс кэша при правках, подсветка отсутствующих настроенных ID, одинаковый порядок нод в реестре
   и на странице (иначе карточка может достаться чужой стране).
9. **Инструмент диагностики** (P1-4): `python -m app.tools.check_nodes` — по каждой ноде печатает
   «настроено», «фактически в панели», чего не хватает, и что делать; код возврата 1 при расхождении.
10. **Гигиена** (P1-1, P1-2): валидация `inbound_ids` при сохранении, страна вместо `xui` в логах,
    `/status` и команде `/nodes`.

**Критерии приёмки:**

* при `inbound_ids=[3]` и панели с инбаундами 1,2 Telegram-сообщение **не** содержит «порт не пускает»;
* в центре алертов — один warn-алерт с фактическими ID панели и без зелёного «отвечает» у ноды;
* `ack` держится после следующей проверки; удаление и выключение ноды (кнопкой и формой) закрывают
  все её алерты;
* `python -m app.tools.check_nodes` на такой ноде печатает расхождение и возвращает 1;
* «проба: N мс» не пропадает из-за ошибки панели, а заменяется на «проба не выполнена: причина»;
* настоящий сетевой отказ (TCP-таймаут) по-прежнему даёт 🔴 «порт не пускает» и совет
  «проверь порты и firewall» — во всех трёх местах: админка, страница подключения, `emergency_check`;
* полный набор тестов зелёный, добавлены регрессии на каждый пункт.

## 7. Что сделать на сервере (без правки кода)

Локальный репозиторий — dev-конфиг (`PANEL_TYPE=fake`, `PANEL_URL` пуст, `data/kometa.db` без нод),
поэтому фактические ID надо смотреть на сервере:

```bash
cd /root/kometa

# 1. Что записано в боте (в первую очередь panel_url и inbound_ids)
sqlite3 data/kometa.db "select id,code,title,panel_url,inbound_ids,is_active from nodes;"

# 2. Что реально в панели ноды — новым инструментом (после выката этой правки)
.venv/bin/python -m app.tools.check_nodes

# 3. Есть ли дубль панели: тот же panel_url у ноды и у PANEL_URL
sqlite3 data/kometa.db "select code,panel_url from nodes;" && grep '^PANEL_URL=' .env

# 4. Живые алерты и дубли отпечатков
sqlite3 data/kometa.db "select id,fingerprint,status,repeat_count,last_seen_at from alerts
                        where fingerprint like 'node:nl%' order by id;"
```

Если ID разошлись — `/admin/nodes?edit=nl`, вписать фактические ID, сохранить, нажать
«Проверить ноды»: алерт закроется на первой успешной проверке. Если `panel_url` ноды совпадает
с `PANEL_URL` — это F18: одна панель опрашивается дважды с разными ID (инструмент это покажет).

### Резервный порт 8443 и добор клиентов

Проверка показала, что 8443 — не мусор: обе ноды отвечают на нём TCP+TLS-рукопожатием
(`TLS www.microsoft.com`, 68–377 мс), а часть клиентов там уже сидела (FI — 8, NL — 14).
То есть второй Reality — это запасной порт, который просто выпал из настроек.

Что сделано:

| Шаг | Результат |
|---|---|
| Настройки FI | `1,2` → **`1,2,6`** (на NL уже стояло `1,2,4`), перезапуск, `check_nodes` — сходится |
| Добор клиентов | `python -m app.tools.sync_inbounds --apply`: **10 клиентов** (8 на FI, 2 на NL) получили профиль на 8443 |
| Проверка | во всех инбаундах обеих нод по 16 клиентов; у выборочных клиентов в подписке 5 конфигов (DE + FI 443/8443 + NL 443/8443), дублей нет |
| Инструмент | оформлен как штатный `app/tools/sync_inbounds.py` (dry-run по умолчанию, `--apply` для записи) |

Почему это не делает `/sync` в боте: он проверяет, что клиент есть **на панели**, а не в

клиентов с настройками по каждому инбаунду (и не переносит клиентов между протоколами:
у AmneziaWG своя форма).

## 8. Что осознанно отложено

* **Дедуп панелей по адресу (F18).** Тихо выкидывать ноду нельзя: именно так исчезнет видимая
  причина расхождения. Сначала предупреждение в админке и в инструменте, дедуп — отдельной задачей.
* **Уникальный индекс `alerts.fingerprint` (F19)** — нужна разовая чистка дублей на проде.
* **Второй Reality/WS-инбаунд и `repeat_count` (F13)** — не влияют на разбор этого инцидента.
* **Нода без `host` не получает отдельного алерта.** Проба сообщает об этом честно
  (`проба не выполнена: у ноды не заполнен host`), но алерт не поднимается: у ноды может быть
  заполнен `sub_base` вручную, и утверждать «сломано» нельзя. При этом для нод, заведённых формой
  админки, `sub_base` собирается из `host` (`registry.for_node`), и пустой host означает, что
  локация молча пропадёт из подписки. Это отдельная задача: добавить `sub_base` в форму и
  предупреждать о пустом host при сохранении (`/admin/nodes`).
* **`check_probes` не проверяет порт, если панель не отдала инбаунды.** Порт в этом случае не
  измеряется вообще; чтобы не терять контроль, нужна проба по сохранённому ранее списку портов —
  отдельная задача (в БД сейчас нет слепка инбаундов).
* **Миграции колонок только для SQLite.** `app/db/session.py` добавляет новые колонки
  (`last_check_error`, `last_probe_error`, `last_probe_stage`) лишь при `dialect == "sqlite"`
  (в докстринге обещан Alembic, но каталога миграций в репозитории нет). Боевая база — SQLite
  (`data/kometa.db`), поэтому сейчас это не мешает; при переезде на PostgreSQL колонки нужно
  добавить вручную:

  ```sql
  ALTER TABLE nodes ADD COLUMN last_check_error VARCHAR(300) DEFAULT '';
  ALTER TABLE nodes ADD COLUMN last_probe_error VARCHAR(300) DEFAULT '';
  ALTER TABLE nodes ADD COLUMN last_probe_stage VARCHAR(16) DEFAULT '';
  ```

  DDL в `_EXTRA_COLUMNS` писать для PostgreSQL нельзя как есть: там нет типа `DATETIME`, а
  `BOOLEAN DEFAULT 0` недопустим — нужен либо полноценный Alembic, либо отдельный набор DDL.
