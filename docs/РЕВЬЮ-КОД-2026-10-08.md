## 1. Вердикт

Это аккуратно спроектированный сервис с редкой для проекта такого размера дисциплиной:
деньги в целых копейках, fail-closed по умолчанию у админки, журнал действий, отдельные
адаптеры платежей, панель-абстракция с fake-реализацией для тестов, 1102 теста без сети.

Проблема не в архитектуре, а в **целостности денежных операций**: подтверждение оплаты —
это «прочитал статус → сходил в панель → записал», без атомарного захвата; состояние
автоплатежа сохраняется раньше коммита; срок подписки меняют три процесса без координации.
Плюс две дыры в боте: **чужие заказы можно отменить/проверить по номеру** (IDOR в
gate-исключённых колбэках) и **обход гейта подписки через `/START`** — обе воспроизведены
на живом коде, а гейт сейчас включён.

Остальное критичное **пока спит**: панель fake, автоплатёж выключен (`AUTOPAY_ENABLED=false`).
Это не повод откладывать — как только включатся автоплатёж и реальная панель, C1/H1/H3/H4
станут рабочими дырами в первый же день, а C2 работает уже сейчас.

## 3. CRITICAL

### C1. VPN за 1 ₽: ветка «код заказа в комментарии» не проверяет сумму

`app/services/autopay.py:171-175`:

```python
code = parse_order_code(payment.comment)      # "Kometa 1234" → 1234
if code is not None:
    for order in pending:
        if order.id == code:
            return order, "по коду заказа в комментарии"   # ← суммы нет вообще
```

`reconcile` сразу вызывает `orders_service.mark_paid` (`autopay.py:236-243`) и отправляет
клиенту «Оплата получена», а админам — «Автоподтверждение оплаты». Номер заказа последовательный
и **сам показан клиенту**: `app/payments/manual.py:41` печатает «В комментарии укажи:
`Kometa {order_id}`».

Сценарий: клиент берёт любой висящий ручной заказ (например, на 959 ₽), переводит **1 ₽**
с комментарием `Kometa 42` — заказ подтверждён, доступ выдан, никто ничего не проверял.

Условие срабатывания: `AUTOPAY_ENABLED=true` и настроенный источник выписки (CSV-файлы банка
или IMAP). Сейчас в `.env` автоплатёж выключен — поэтому это **спящая** дыра, но именно её
включают первой при запуске СБП-приёма.

**Починить:** в ветке по коду требовать совпадение суммы (`payment.amount_kopecks >=
order.pay_amount_kopecks` или `abs(...) <= tolerance`), иначе — в несопоставленные с алертом
админам. Тест: платёж 100 копеек с комментарием `Kometa <id>` не должен подтверждать заказ;
платёж ровно на `pay_amount_kopecks` — должен.

### C2. Чужие заказы по номеру: IDOR в колбэках `order:*` (воспроизведено)

Три обработчика берут заказ **только по id из callback_data**:

```python
# buy.py:287-298 — обратите внимание: user в обработчик даже не передаётся
@router.callback_query(F.data.startswith("order:cancel:"))
async def cb_cancel(call: CallbackQuery, session: AsyncSession) -> None:
    order = await orders.get_order(session, int(call.data.rsplit(":", 1)[1]))
```

`orders.get_order` (`orders.py:137-138`) — это `session.get(Order, order_id)` без проверки
владельца. При этом все три префикса (`order:cancel:`, `order:manual:`, `order:check:`)
**исключены из гейта подписки** (`middlewares.py:32,155-156`), то есть доступны любому
пользователю, даже не подписанному на канал, а `callback_data` в Telegram формирует клиент —
её можно отправить произвольной.

Последствия (id заказов последовательные):

* `order:cancel:<чужой id>` — отменяет чужой висящий заказ (воспроизведено: пользователь 6002
  отменил заказ пользователя 6001). Сейчас это «всего лишь» потерянная продажа (счёт Stars
  потом не проходит pre-checkout, `buy.py:418-420`), но при включённых ручных переводах отмена
  освобождает уникальные копейки (`orders.py:28-38` учитывает только pending), и платёж жертвы
  может быть сопоставлен **другому** заказу;
* `order:check:<чужой id>` — запускает проверку платежа; если провайдер подтвердит оплату,
  доступ выдаётся владельцу заказа, а **ссылка-подписка уходит тому, кто нажал**
  (`buy.py:390-395`). Сейчас латентно только потому, что `stars.check_payment` всегда
  возвращает PENDING (`stars.py:157-163`) — включаем крипту/WATA/Platega, и дыра открывается;
* `order:manual:<чужой id>` — рассылает админам «Подтвердить?» с именем атакующего
  (`buy.py:313-328`): спам по админам и путаница в ручной сверке.

**Починить:** во всех трёх обработчиках сверять владельца (`order.user_id != user.id →
ORDER_NOT_FOUND`), в `cb_cancel` добавить зависимость `user`. Тест: `order:cancel:<чужой id>`
не меняет статус чужого заказа.

## 4. HIGH

### H1. `external_id` не заменяется на id счёта провайдера

`app/services/orders.py:85` создаёт заказ с `external_id=f"ord-{uuid4().hex[:16]}"`, а
`app/bot/handlers/buy.py:241-243` подставляет id счёта только при условии
`if order.external_id == f"ord-{order.id}"` — оно **никогда** не выполняется (16 hex-символов
против десятичного id). Никакой другой код это поле не пишет (проверено grep по `app/`).

Последствия:

* `job_check_crypto` (`main.py:96`) и кнопка «Проверить оплату» (`buy.py:347`) передают в
  `check_payment("ord-…")`: Crypto Pay отвергает нецифровой id (`cryptobot.py:236`), WATA —
  свой формат (`wata.py:237-239`), Platega делает GET `/transaction/ord-…` → ошибка. Опрос
  как страховка не работает ни у одного провайдера;
* резервный поиск заказа по id транзакции в вебхуке Platega (`payments.py:337-341`) не может
  сработать **никогда** — а именно этот путь назван в тестах «ключевым риском автовыдачи»;
  вебхук без `payload` и **любой чарджбэк** (`payments.py:250`) остаются несопоставленными:
  деньги не зачислены, возврат не отключил доступ.

**Починить:** после `create_invoice` присваивать `order.external_id = invoice.external_id`
безусловно (уникальность сохранить), либо завести отдельную колонку под id провайдера.
Тест: создание заказа через фейкового провайдера → `external_id` равен id счёта, и
`check_payment` вызывается с ним. Существующий `test_platega_webhook.py:231` подставляет
`external_id` руками — поэтому дефект и не виден.

### H2. Оплата по отменённому/просроченному заказу теряется молча

`mark_paid` для статусов `canceled|expired` возвращает `(None, False)` (`orders.py:166-169`),
вебхуки уведомляют только при `sub is not None` (`payments.py:94, 215, 365`), но событие
`ORDER_PAID` пишут безусловно (`payments.py:86-91, 201-212, 352-362`).

Сценарий: клиент создал заказ со скидкой, затем второй — `_cancel_other_discounted`
(`orders.py:115-134`) отменил первый; клиент оплачивает именно первый счёт. Вебхук отвечает
200, деньги списаны, заказ остался `canceled`, админам ничего не пришло, а журнал утверждает
«Заказ оплачен». Так же ведёт себя заказ, который `job_expire_orders` закрыл через 30 минут,
пока банк проводил платёж.

**Починить:** подтверждённый платёж по не-pending заказу либо зачислять (перевести в `paid` и
выдать доступ), либо поднимать алерт и писать событие только по факту перехода.

### H3. `mark_paid` — не атомарный check-then-act

Идемпотентность держится на чтении объекта в памяти (`orders.py:166-167`), запись — после
похода в панель (`subscriptions.activate_plan`, `subscriptions.py:320-349`), а продление на
панели аддитивно (`xui.py:846`, `fake.py:91`). Два подтверждения, наложившихся в одном цикле
событий (повторная доставка вебхука, вебхук + кнопка «Проверить оплату», вебхук +
`job_check_crypto`), оба видят `pending` и оба продлевают срок: клиент получает 2×дней за одну
оплату, в БД — одна. Награда рефереру тоже может начислиться дважды (`referral.py:100-127`).
Всё живёт в одном процессе/цикле (`main.py:246-317`), так что чередование происходит на каждом
`await`.

**Починить:** переход через compare-and-swap (`UPDATE orders SET status='paid' WHERE id=:id AND
status='pending'` + `rowcount`), и только победитель идёт в панель; либо уникальная запись
«платёж применён». `SELECT … FOR UPDATE` в SQLite нет — опираться на условный UPDATE.
Тест: два параллельных `mark_paid` на один заказ (`asyncio.gather`) → одно продление.
Сейчас в тестах нет ни одного конкурентного сценария (`grep -c "gather|create_task" tests/` → 0).

### H4. Автоплатёж: состояние сохраняется раньше коммита, уведомления — до него

`reconcile` пишет `last_check` и список обработанных ключей (`autopay.py:302-308`) внутри себя,
коммит делает вызывающий (`main.py:113-120`), а уведомления клиенту и админам уходят ещё раньше
(`autopay.py:264-271, 276-296`). Любая ошибка на `session.commit()` (в том числе
`SQLITE_BUSY`, см. M5) → исключение, откат (заказ снова `pending`, подписки нет), но квитанция
уже в `processed`, окно сдвинуто → **платёж не будет рассмотрен повторно**. Клиент при этом
уже получил «Оплата получена! Подписка активна», админ — «Автоподтверждение».
Ручное подтверждение после этого продлит панель второй раз.

**Починить:** сначала коммит БД (включая отметку обработки — лучше в БД, а не в JSON),
потом уведомления; `last_check` двигать только после успешного коммита.

### H5. Гонка «истечение ↔ продление»

`disable_expired` (`subscriptions.py:605-629`) выбирает истёкшие подписки, затем по каждой
последовательно ходит в панели и пишет `status="expired"` в **устаревший** объект сессии.
Продление, попавшее в это окно (`mark_paid` → `activate_plan`: статус `active`, панель продлена,
свой коммит), будет перезаписано: джоба закоммитит `expired`, а выключение на панели может
прийти после продления. Итог — деньги взяты, доступ выключен. Окно растёт с числом подписчиков,
потому что вызовы панели последовательные.

**Починить:** перед выключением перечитать `expires_at` (или версионировать строку) и
пропускать подписки, изменённые после выборки.

### H6. Ошибка выключения на панели при истечении проглатывается и не повторяется

`subscriptions.py:618-624`: при `PanelError` — `pass`, но статус всё равно `expired`, а
следующий прогон выбирает только `trial|active`, то есть клиента на панели больше никто не
выключит. `/sub/{token}` продолжает отдавать конфиги для `expired` (проверяется только
`blocked`, `sub.py:389`; дыра даже задокументирована в `tests/test_connection_audit.py:265`).
Один таймаут панели в момент истечения = бесплатный доступ на неопределённый срок.

**Починить:** ставить `expired` только после успешного выключения либо завести флаг
`needs_disable`, который повторяется фоновой задачей.

### H7. Компенсация простоя: частичный сбой → двойное начисление при повторе

`downtime.finish` (`services/downtime.py:202-234`) проходит по всем активным подпискам и
продлевает их на панелях. Изоляции ошибок по подписчикам нет: `PanelError` на одной подписке
прерывает транзакцию **после** того, как предыдущие панели уже продлены; откат возвращает
`ended_at/days/granted_at`, период остаётся открытым. Админ повторяет закрытие — и те, кому уже
продлили, получают дни второй раз. Дополнительно: `infra.py:710-734` и `675-698` не оборачивают
вызовы в `try/except`, поэтому оператор видит 500 вместо объяснения.

**Починить:** изолировать сбои по подписчикам (как в `disable_expired`), фиксировать
`granted_at` до начисления, пропускать уже награждённых; в панели — `try/except` → flash-ошибка.

### H8. Чарджбэк Platega не помечает заказ возвращённым

`_revoke_after_refund` (`payments.py:244-266`) выключает подписку и пишет событие
`order_refunded`, но `orders.status` остаётся `paid`. Все отчёты считают выручку по `paid`
(`stats.py:105, 200, 235, 341`), а `refund_summary` возвраты — по `refunded` (`stats.py:281-285`).
Итог: возвращённые банком деньги остаются в обороте и прибыли, в отчёте возвратов их нет.

**Починить:** `status="refunded"`, `refunded_at`, `refunded_by="platega-webhook"`.
Тест: чарджбэк → заказ не в выручке, сумма в отчёте возвратов.

### H9. Обход гейта подписки через регистр команды (воспроизведено)

`_command_name` приводит команду к нижнему регистру (`middlewares.py:142-146`), поэтому
`/START`, `/Start`, `/start@бот` попадают в `ALWAYS_ALLOWED_COMMANDS` и гейт их пропускает.
Но aiogram сравнивает команды **с учётом регистра** (`CommandStart`, `ignore_case=False` по
умолчанию), поэтому такой апдейт не доходит до хендлера `/start`, падает в `fallback_text`
(`fallback.py:20-25`) и показывает **главное меню** — то есть ровно то, что гейт должен
закрывать («ни кнопки, ни текст», `channel_gate.py:3-6`). Заодно теряется реферальный payload
такого апдейта (пригласивший не привязывается).

Гейт включён в `.env` (`CHANNEL_GATE_ENABLED=true`), так что это живой дефект, а не теория.
Отдельные кнопки по-прежнему закрыты гейтом — обходится именно экран и контракт.

**Починить:** сравнивать команду без приведения регистра (или сверять `message.text` целиком
через `CommandStart()`), и как страховку — перепроверять вердикт гейта внутри `fallback_text`.
Тест: `/START` и `/Start` показывают экран подписки; `/menu` — тоже.

## 5. MEDIUM

**M1. Platega: не связаны сумма, транзакция и заказ.** После проверки заголовков
(`payments.py:303-306`) вебхук перепроверяет только **статус** транзакции (`:317-329`) и
разрешает заказ из тела (`payload` → `order:<id>`, `:337-343`), а `check.amount`
(`platega.py:346`) игнорируется. Комментарий в коде обещает, что утечка `X-Secret` не даёт
бесплатного доступа (`:284-285`), но с секретом достаточно переиграть **одну свою реально
оплаченную дешёвую** транзакцию с `payload` дорогого заказа. Частичная оплата и валюта тоже
не проверяются. Fix: сверять `transaction_id` со сохранённым id заказа и сумму в копейках,
предпочитать id транзакции телу.

**M2. WATA: возврат не отключает доступ.** `payments.py:167-175` только уведомляет админов
(«доступ не отключаем — это решение человека»), тогда как Platega отключает. Одинаковый риск —
разное поведение. Плюс на платёжной ветке не проверяется `kind` (`Payout` со статусом `Paid`
попадёт в зачисление) и не сверяется `amount`.

**M3. Одинаковые копейки у двух заказов.** `_allocate_pay_kopecks` (`orders.py:28-38`) читает
занятые сигнатуры без уникального индекса; заказ флашится (`:89`) в транзакции, которая держится
через внешний HTTP `create_invoice` (до 30 с) до коммита. Два покупателя одного тарифа получают,
например, `199.13`; автоплатёж зачислит **старейший** pending (`autopay.py:178-180`) — возможно,
чужой. Плюс ветка «сумма без копеек» (`autopay.py:183-185`) подтверждает заказ автоматически,
хотя её текст обещает «уточнить вручную». Fix: частичный уникальный индекс
`(amount_rub, pay_kopecks) WHERE status='pending'`, а ветку без копеек — в несопоставленные.

**M4. Несопоставленные поступления нигде не хранятся.** `autopay.py:273` помечает ключ
обработанным и для них тоже; сервис не поднимает `Alert`, хотя виды `payment_unmatched`/
`statement_error` в `alerts.py:33-34` есть. Если сообщение в Telegram пропустили или
`AUTOPAY_NOTIFY_UNMATCHED=false`, деньги больше не всплывут. Fix: сохранять поступление
(строка `Payment`/алерт) и повторять, пока не разобрали.

**M5. SQLite без WAL и `busy_timeout`.** `DB_URL` пуст → `sqlite+aiosqlite:///…/kometa.db`
(`config.py:325-329`), движок создаётся без прагм (`db/session.py:14`): писатели ждут 5 с и
получают «database is locked». Вебхуки и панель держат транзакцию через сетевые вызовы, так
что это не теория. Fix: `PRAGMA journal_mode=WAL`, `busy_timeout`, короткие транзакции; на
росте — Postgres (путь через Alembic уже упомянут в `session.py:68-73`).

**M6. Отчёты.** Разные окна у одной страницы: `revenue_by_day` — календарные дни
(`stats.py:190-192`), остальные — скользящие `now - days*24h` (`:101,231,278`). `profit_summary`
вычитает ровно один месяц расходов при периоде 7/30/90 (`:290-304`) — на 90 днях прибыль
завышена на ~2 месяца. Звёздное нетто считается по прайсу, а не по фактически уплаченным
звёздам (`stats.py:143-149` vs `order.stars_amount`). `finance._call` превращает любую ошибку
отчёта в ноль (`finance.py:30-39`). Fix: один помощник окна, пропорциональные расходы,
`order.stars_amount or plan.price_stars`, явный флаг «отчёт не посчитан».

**M7. Начисление дней без верхней границы.** `users.py:233-248` (`abs(days)`) — опечатка
`100000` молча выдаёт десятилетия; в тарифах (`growth.py:83`) и простое (`downtime.py:37`)
лимиты есть. Fix: 1…730 + подтверждение крупных значений.

**M8. Неограниченные выборки.** `_redemptions_by_promo` тянет все применения до 100 кодов,
чтобы оставить по 3 (`growth.py:185-193`); `_audience_ids` материализует все `tg_id`
(`growth.py:499-503`); финансы трижды сканируют одни и те же оплаченные заказы и агрегируют в
Python (`stats.py:102-108, 232-238, 294`). Fix: `LIMIT`/оконные функции, стриминг аудитории,
агрегация в SQL.

**M9. CSV-формулы.** См. A6 в ревью панели: `exporting.to_csv` (`exporting.py:90-107`) не
нейтрализует `= + - @`, а в файл попадают имя из Telegram, метки, комментарий заказа, payload.

**M10. Дыры журнала.** Сообщение клиенту (`users.py:483-502`) и массовые действия
(`orders.py:450-455` — только агрегат) не оставляют отдельных записей; удаление заметки
пишется как «добавил заметку» (`users.py:472`).

**M11. Почтовый источник выписки.** Регекспы (`statements_sources.py:1120-1146`) не понимают
суммы без копеек («Поступление 199 ₽») и не проверяют валюту — письмо просто не распознаётся,
и алерта о несопоставленном поступлении не будет. CSV-путь целые рубли обрабатывает корректно.

**M12. Рост данных и мёртвый код.** Ретеншена нет ни у `events`, ни у закрытых `alerts`, ни у
`broadcasts` (`grep "delete(|retention" app/` → 0). Таблица `payments` объявлена
(`db/models.py:208`), но не пишется. `matching.Money`/`amounts_match` — единственный
толерантный помощник сверки, и production-путь его не вызывает.

**M13. Произвольный `callback_data` роняет обработчик.** `buy.py:202` (`_, plan_id,
provider_code = call.data.split(":")`) и `int(...)` в `:111,192,289,303,333` падают
`ValueError` на данных вида `pay:7`, `plan:abc`, `order:cancel:xyz`. Глобального обработчика
ошибок нет (`dispatcher.errors` не зарегистрирован), поэтому aiogram логирует и **молча
дропает апдейт**: у клиента «крутится» кнопка без ответа. Лечится try/except вокруг разбора
плюс `call.answer(...)`, и регистрацией обработчика ошибок с уведомлением админов.

**M14. Антифлуд: течёт память, а кнопка проверки обходит кэши.** `_hits` в
`middlewares.py:113-138` никогда не чистится (запись на каждого пользователя навсегда), а
`channel:check` вызывается с `force=True` (`handlers/channel.py:32`), что отключает
положительный, отрицательный кэши и backoff (`channel_gate.py:180-186`) — каждое нажатие идёт
в Telegram. При 5 действиях / 3 с на пользователя это возвращает ровно тот расход лимитов API,
от которого гейт защищался. Fix: чистить `_hits` и держать кулдаун 3–5 с на кнопку проверки.

**M15. Кэш успешной подписки — до 12 часов после отписки.** `channel_verified_at` не
перепроверяется (`channel_gate.py:96-107,180-181`, `config.py:46`): человек подписался,
получил доступ, вышел из канала — и до 12 часов бот его пускает без запросов к API.
Компромисс осознанный, но его стоит либо сократить (1–3 часа), либо перепроверять при первом
«настоящем» действии, и обязательно описать в README/`.env.example`.

**M16. Конфигурация: умолчания, которые молча отключают защиту.** `CHANNEL_GATE_FAIL_OPEN=true`
(`config.py:50`) при самой частой ошибке настройки (бот не админ канала) превращает гейт в
декорацию — кроме одного предупреждения в час. `admin_id_list` (`config.py:271-272`) молча
выбрасывает неразобранные id: опечатка в `ADMIN_IDS` даёт **ноль админов** — без алертов, без
админ-команд, а сами админы попадают под гейт. `AUTOPAY_TOLERANCE_KOPECKS>0` ослабляет точное
совпадение суммы, а >100 копеек позволяет меньшему платежу закрыть больший заказ. Комбинация
`ADMIN_LOCAL_ONLY=true` + `ADMIN_TRUST_PROXY=false` за прокси превращает «только localhost» в
«пускаем всех» (см. A10 в ревью панели). Fix: валидировать на старте и падать с понятным
текстом, а не работать «тихо и не так».

**M17. Рассылка из бота — без лимита и внутри апдейта.** `handlers/admin.py:522-539` грузит
всех незаблокированных пользователей и рассылает по одному сообщению, удерживая сессию
middleware; на большой базе это часы, теряется при рестарте, не имеет прогресса/отмены — и
дублирует уже существующий панельный механизм рассылок (`Broadcast` + `_run_broadcast`).

**M18. Соединение пула удерживается на время запроса к Telegram.** Сессия открывается в
`DbSessionMiddleware` (`middlewares.py:44-52`) и живёт весь апдейт, а `channel_gate.verdict`
внутри неё делает `get_chat_member` (`channel_gate.py:147,177`). Апдейты обрабатываются
параллельно (`handle_as_tasks=True`), пул по умолчанию 5+10 — всплеск (например, после
рассылки) упирается в таймаут пула и теряет апдейты. Fix: проверять канал в короткой отдельной
сессии до открытия основной, либо ограничить параллелизм (`tasks_concurrency_limit`).

## 7. Что сделано хорошо

* **Слои и границы.** `bot/handlers → services → db`, платежи — адаптеры с реестром
  (`payments/registry.py`), панели — абстракция с `FakePanel`, реестр панелей с инвалидацией
  кэша при правке ноды. Видно, что структура проектировалась, а не сложилась.
* **Деньги в целых.** Рубли и копейки — `int`; `Decimal` там, где валюта не рубль
  (`cryptobot`/`stars`/`platega`); скидки считаются с полом до рубля и потолком
  (`promo.py:80-94`), звёзды не уходят в ноль.
* **Проверка подлинности вебхуков.** Crypto Pay — HMAC-SHA256 от сырого тела
  (`payments.py:33-43`), WATA — RSA-SHA512 с `cryptography`, Platega — fail-closed по
  заголовкам и обязательная перепроверка через API. Неизвестные статусы трактуются как «не
  оплачено».
* **Идемпотентность выписок.** Состояние обработки, дедуп по отпечаткам, атомарная запись файла
  состояния (`os.replace`), окно не сдвигается при ошибках чтения, нераспознанная хвостовая
  строка не помечается обработанной.
* **Время.** `TZDateTime` нормализует naive/aware (`models.py:32-50`), всё хранится в UTC,
  смешения типов не найдено.
* **Безопасность слоя панели.** Fail-closed, PBKDF2-SHA256 240k, `compare_digest`, подписанная
  cookie, роли с capability-матрицей, полная инвентаризация маршрутов (39 POST/19 GET — все под
  проверкой), автоэкранирование Jinja, отсутствие SQL-инъекций, маскировка токена панели.
* **Гейт подписки на канал.** Клиентской логике можно позавидовать: явные исключения
  (админы, активная подписка, `/start`, `/support`, «Я подписался», `successful_payment`,
  кнопки уже созданного заказа), негативный кэш 15 с, backoff после сбоя, напоминание админам
  раз в час, стартовая самопроверка «бот админ канала?», и всё это покрыто 23 тестами.
* **Культура документации.** `docs/` описывает не только «что», но и «почему»; макеты
  собираются из живых шаблонов (`design/build.py`), есть тест-санитайзер публичных формулировок,
  скрипты по умолчанию dry-run с бэкапом и блоком «как проверить».

## 8. Качество тестов

**Сильные стороны.** 1102 теста, 68 с, без сети: `FakePanel`, ASGI-транспорт для веба,
monkeypatch реестра панелей, подмена сессии. Покрыты роли и запреты по страницам, вебхуки
(включая подписи), форматы подписки, парсеры выписок, юридические тексты, скрипты, TLS-флаги.
Тесты читаются как спецификация.

## 9. План работ

**P0 — до включения автоплатежа и продаж (день-два)**

1. **C1** — проверка суммы в ветке по коду заказа (+ тест).
2. **C2** — проверка владельца во всех трёх колбэках `order:*` (+ негативные тесты): это
   единственная критичная дыра, доступная прямо сейчас, при включённом гейте.
3. **H9** — регистр команды и перепроверка гейта в `fallback_text` (+ тест на `/START`).
4. **H1** — присвоение `external_id` от провайдера (+ тест); проверить, что опрос и резервный
   поиск в вебхуках после этого реально работают.
5. **H3 + H4** — атомарный переход заказа и порядок «коммит → уведомления» в автоплатеже.
6. **A2/A3/A1 из ревью панели** — массовые действия по заказам, семантика возврата и отзыв сессий:
   это то, чем модератор пользуется каждый день.
7. **M13** — разбор `callback_data` в try/except и обработчик ошибок диспетчера: сейчас «кривая»
   кнопка оставляет клиента без ответа.

**P1 — устойчивость и деньги (неделя)**

8. **H5/H6/H7** — перечитать состояние перед выключением, повторять неудачные выключения,
   изолировать сбои в компенсации простоя.
9. **H8 + M1 + M2 + M3 + M4** — привести возвраты и сверку сумм к одному правилу: сумма и
   транзакция связаны с заказом, чарджбэк = `refunded`, несопоставленное хранится и повторяется.
10. **M5 + M18** — WAL/`busy_timeout` (или Postgres), короткие транзакции, не держать сессию и
    соединение через сетевые вызовы; после этого перепроверить H3/H4.
11. **M6/M8/M9/M10** — отчёты, неограниченные выборки, CSV, журнал (в панели — A6/A7/A12).
12. **M7/M11/M16** — лимиты на ручные начисления, парсер писем, валидация конфигурации на старте.
13. **M14/M15/M17** — кулдаун кнопки проверки и чистка антифлуда, TTL кэша гейта, ограниченная
    рассылка из бота (или перевод на панельный раннер).

**P2 — гигиена**

14. **M12/L5/L7/L8/L9–L12** — ретеншен, мёртвый код, актуализация HANDOFF/README,
    `ruff` + `pytest-cov` в dev-зависимости и в CI-скрипте.
15. Конкурентные тесты как отдельный набор (`tests/test_concurrency.py`) хотя бы для четырёх
    сценариев из §8 — иначе гонки вернутся при следующей правке.

**Незакоммиченная сетка 120 ₽ — отдельный шаг выката.** `seed_plans` только добавляет
отсутствующие тарифы и никогда не перезаписывает цену (`db/session.py:92-114`), поэтому на
базе, которая уже живёт, цены останутся прежними, а юридические документы и константы уже
новые. В локальной `data/kometa.db` сетка 120/299/539/959 (проверено), но тест
`test_price_consistency.py:60-66` проверяет только свежий сид — расхождение на чужой базе он не
поймает. Перед выкатом: `.venv/bin/python -m app.tools.set_prices --grid 120 --apply` на целевой
БД и сверка `/admin/plans` с прайсом; лучше — стартовая проверка «тарифы в БД = константы».

**Быстрый чек-лист перед следующим выкатом**

```bash
.venv/bin/python -m pytest -q                 # ожидаем 1102+ зелёных
.venv/bin/python -m app.tools.emergency_check # готовность аварийного уровня
git status --short                            # в дереве не должно быть незакоммиченных правок панели/платежей
```

Плюс три сценария руками: (1) подтвердить заказ вебхуком и кнопкой одновременно — срок должен
вырасти один раз; (2) выключить учётку модератора и повторить запрос с её прежней cookie —
должен быть редирект на вход; (3) отправить боту `/START` и `/start` — оба должны показать экран
подписки (при включённом гейте).
